# Claude Code: жёсткий редизайн приложения командой агентов (v2, заменяет прежний промпт)

Ветка `claude/app-redesign` от свежего `origin/main`. Не трогай `supabase/` и `api/`. Если `main` не собирается или A0c / `claude/fonts-cyrillic` не влиты, остановись и скажи, чего не хватает.

## Диагноз владельца (не обсуждается, это исходные данные)
1. **Тема неединая.** Кожа `app-skin.css` покрыла только список объектов и обзор. Вкладки, вход, фото, проблемы, тариф, экраны рабочего и клиента остались в старом виде. Для платящего клиента это выглядит как «два разных продукта».
2. **Шрифт не нравится владельцу вообще.** Plex Sans Condensed в заголовках и Plex Sans в тексте снимаются как решение по умолчанию. Остаются только если выиграют сравнение по критериям ниже.
3. **Нужна жёсткая проверка, а не вежливое согласие.** Любой агент, который пишет «в целом хорошо», работает плохо.

## Входные файлы
- `docs/design-inputs/buildproof-decisions.md` (если нет в репо, положи из чата и закоммить), `docs/contracts/reports.md`, `docs/screens/*`, `landing-prototype/`.
- **Внешняя критика сайта** от другого ИИ: `docs/design-inputs/external-critique-landing-2026-11-25.md`. Она про лендинг, но по ней же судим тон и доверие внутри приложения. Агент «Контролёр» обязан разобрать её пункт за пунктом (принять / отклонить с причиной). Отклонять без причины нельзя. Заранее известные границы: нельзя выдумывать кейсы, цифры клиентов, отзывы, фото; «Уже 7 объектов» только если это правда; гарантию денег и реквизиты (`src/config/legal.ts`) решает владелец, агенты оставляют их в списке «ждёт владельца».
- **Итоги встречи с экспертом:** `<<ВСТАВИТЬ ИТОГИ ВСТРЕЧИ или написать «нет»>>`. Если «нет», работай без них и не спрашивай.
- Продукт: B2B SaaS для владельцев малых строительных фирм Эстонии. Владелец смотрит с телефона, рабочие отчитываются фото. Принципы: «нет данных ≠ нет проблем»; принято / ждёт проверки ○ (скачок > 25) / проверено ✓; оффлайн не обещаем; касание ≥ 48 px; шрифт ≥ 17 px; статус всегда формой и текстом.

## Этап 0 (до команды): инвентаризация, без правок
Агент-аудитор выполняет сам:
1. Перечисляет **все** маршруты и экраны из роутера (владелец, бригадир, рабочий, клиент, вход, регистрация, тариф, ошибки, пустые состояния). Таблица `docs/design/00-inventory.md`: маршрут, роль, обёрнут ли в `.bp`, какой шрифт реально применён, есть ли жёсткие цвета.
2. Находит расхождения командами: `grep -rnE "#[0-9a-fA-F]{3,8}|rgb\(" src --include=*.tsx --include=*.css` (цвета вне токенов), `grep -rn "font-family" src`, поиск классов Tailwind с жёсткими цветами (`bg-gray-`, `text-slate-`, `bg-blue-` и т.п.).
3. Снимает скриншоты **каждого** экрана 390×844, светлая и тёмная тема. Это baseline «до».
Результат: число экранов вне новой темы и число жёстких цветов. Это цифры, которые нужно довести до нуля.

## Команда (каждому свой файл в `docs/design/`, общий `design-brief.md`)
Любое расхождение решается правкой `design-brief.md`, а не «договорённостью».

1. **Бизнес-архитектор → `01-business-flow.md`.** Для каждой роли: путь от входа до главного действия, цена ошибки, метрика активации. По каждому экрану одно главное действие. Обязан ответить на вопросы из критики: чем это лучше WhatsApp-группы, как снять страх «рабочие не будут пользоваться», что видит владелец в первый день.
2. **Исследователь → `02-research.md` и `02-type.md`.**
   - Конкуренты: PlanRadar, Fieldwire, Procore, Buildertrend, Estonian ehituspäevik-решения. Только проверяемые открытые страницы, ссылки обязательны. 5 решений, которые берём, 5 антипримеров.
   - **Шрифты:** 3 кандидата с кириллицей и эстонской латиницей (õ ä ö ü š ž), без Plex. Проверить в списке: Inter / Manrope / Golos Text / Onest / Geologica / Roboto Flex / PT Sans, исключить все, у кого нет `tnum` или нормальных цифр. Критерии: читаемость на 390 px на улице, цифры процентов (табличные), вес файла после subset (≤ 120 КБ на гарнитуру), лицензия OFL, самохостинг (без Google Fonts-запросов), характер «надёжный, не стартап-игрушка». Результат: ровно один фаворит и один запасной, с рендером в `docs/design/type-test/`.
3. **UX-проектировщик → `03-wireframes.md` + `03-screens.json`.** Для каждого экрана из инвентаря: блоки по важности, состояния (пусто, загрузка, ошибка, принято, ждёт проверки, нет отчётов, «не отправлено»), навигация. Mobile-first 390 px, затем десктоп. Максимум 1 главная кнопка на экран.
4. **Контент → `04-copy.md`.** Русский, английский, черновик эстонского (`TODO native ET review`). Язык боли и результата, не описания функций. Запрещено: слово «реальное», обещания оффлайна/геолокации/SMS, самообесценивание («без громких обещаний» наверху), `[плейсхолдеры]` в видимом тексте. Тест: строки `ru.json` без латиницы, кроме имён и единиц.
5. **UI-дизайнер → `05-ui.md` + код.**
   - **Единые токены** в `src/styles/tokens.css`: цвет, шрифт, размеры, радиусы, тени, тёмная тема. Одна тема на весь продукт, включая вход, вкладки, экраны рабочего и клиента.
   - Замена шрифта на победителя из `02-type.md`: self-hosted woff2 subset (cyrillic, latin, latin-ext), `font-display: swap`, `tnum` на процентах и датах.
   - Компоненты: кнопка, чип статуса, карточка объекта, карточка отчёта, строка этапа, плашка «не отправлено», вкладки, поле формы, пустое состояние.
   - **Принудительная проверка:** добавить в `npm run lint` скрипт `scripts/check-tokens.mjs`, который падает при любом hex/rgb вне `tokens.css` и любом `font-family` вне него. Без этого PR не принимается.
   - Никаких новых UI-библиотек.
6. **Контролёр → `06-audit-<этап>.md` после каждого этапа.** Роль «Март»: владелец фирмы из-под Тарту, 52 года, обжёгся на софте, не любит красивое без пользы. Для каждого этапа нумерованные возражения HIGH/MED/LOW с конкретным исправлением. Проверяет: единую тему (сравнивает скриншоты **всех** экранов рядом, при любом выбивающемся экране это HIGH), шрифт, тупики, нагрузку, контраст (AA, рабочий экран AAA), касания, английские строки, невыполнимые обещания, разбор внешней критики. **Запрещено писать «в целом хорошо».** Если HIGH нет, обязан найти минимум 5 MED. **Право вернуть работу на любой прошлый этап.** Дальше идти нельзя, пока есть HIGH.

Порядок: 0 → 1 → (К) → 2 → (К) → 3 и 4 параллельно → (К) → 5 → (К) → реализация → финальный аудит по скриншотам.

## Реализация
Приоритет: (1) единая тема и шрифт на **всех** экранах, это первый PR-коммит; (2) список объектов и пусто; (3) обзор объекта; (4) «Сегодня» рабочего и отправка отчёта; (5) очередь проверки; (6) проблемы, фото, клиентская страница; (7) вход, регистрация, «Тариф». Если нужен бэкенд Codex, делай по `docs/contracts/reports.md` на заглушках с `// TODO backend`.
