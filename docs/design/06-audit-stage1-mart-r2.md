## HIGH

### 1. Весь путь рабочего держится на почте, которой сейчас нет. Документ пишет «после этого PR можно». HIGH
**Где:** §0.3 «После этого PR можно», §5.2 строка 1 («**этот PR**»), §3.2 шаг 3, §3.4 шаг 1, K18, §8 п.18.
**Что в коде:** `SignupSection.tsx`, комментарий к компоненту: «Magic link / e-mail code are off until we have our own domain and SMTP». То есть своего SMTP нет — это зафиксировано в коде. Стандартная почта Supabase шлёт письма только на адреса участников проекта Supabase, а не на почту рабочего. `api/invite.ts` возвращает `201` сразу после `inviteUserByEmail`. Доставку письма никто не проверяет.
**Что увижу я:** нажимаю «Пригласить (3)», вижу «приглашён» по всем трём строкам. Рабочим ничего не приходит. Через 7 дней у меня красное «7 дней без первого отчёта» и кнопка «Пригласить ещё раз» (она тоже не сработает, см. HIGH 2). Продукт сказал мне «приглашён» — и соврал. Это ровно «софт, которым никто не пользовался», только теперь виноват я, а не программа.
**Почему это не снимает K18:** K18 стоит в конфликтах как «ждёт Codex + владельца», а §5.2 и §3.2 называют путь «этот PR». Условие из §8 п.18 («не называем надёжным») — оговорка в конце, а не шлюз.
**Исправить:**
- В §8 первым пунктом поставить шлюз: «Главное действие дня 0 “Пригласить рабочего” выходит в продакшен только после проверки на стенде: свой SMTP, письмо доходит на Gmail/Outlook/mail.ee, ссылка открывает `/project/:id/today`». До этого в §5.2 строка 1 — «ждёт SMTP», а не «этот PR».
- В §3.2 шаг 3 заменить итог «приглашён» на «письмо отправлено на {почта}. Если рабочий не видит письмо через 10 минут — проверьте папку «Спам»». Слово «приглашён» не использовать, пока нет признака входа.
- Добавить в §3.2 шаг 3в «рабочий говорит: письма нет» с главным действием (см. HIGH 2, исправление).
- В §7 добавить вопрос владельцу: кто и когда подключает SMTP. Это блокер активации ранга А, а не ранга «В».

### 2. Повторно пригласить рабочего нельзя, а рабочий без пароля не может войти снова. HIGH
**Где:** §3.2 шаг 3б («Пригласить ещё»), шаг 4 и §5.3 (главное действие «Пригласить ещё раз» на 3–6 и 7+ днях), §3.4 шаг 2 («Другой браузер → … новое приглашение»), §4 «Задайте пароль» («рабочему не навязываем»).
**Что в коде:** `api/invite.ts` для уже существующего e-mail:
- либо `inviteUserByEmail` отвечает ошибкой «already registered» → `409 email_unavailable`;
- либо Supabase возвращает того же пользователя, и следующая вставка `profiles` с тем же `id` падает на первичном ключе → ветка `catch` → `admin.auth.admin.deleteUser(invited.user.id)`. Это удаляет уже приглашённого рабочего вместе с `project_access` (каскад) и отменяет первое письмо.
В обоих случаях письмо повторно не уходит. Ссылка из письма-приглашения живёт ограниченное время (настройка срока OTP в Supabase Auth, по умолчанию — часы, а не дни). Рабочий, который открыл письмо на следующий день, получает просроченную ссылку, пароля у него нет, `/login` требует пароль.
**Что увижу я:** главная кнопка на красном объекте — «Пригласить ещё раз». Нажимаю — «ошибка: почта занята». Или хуже: человек исчезает из списка. Рабочий сменил телефон — то же самое. Выхода из тупика в документе нет.
**Исправить (всё на фронтенде, бэкенд не трогаем):**
- «Пригласить ещё раз» для уже приглашённого человека заменить на «Отправить ссылку для входа»: `supabase.auth.signInWithOtp({ email, options: { shouldCreateUser: false, emailRedirectTo: …/login } })`. Пользователь уже есть, новый не создаётся, `api/invite.ts` не вызывается. Владелец вводит почту ещё раз (почты в `profiles` нет).
- На `/login` добавить вторую кнопку для всех: «Войти по ссылке на почту» (тот же `signInWithOtp`). Это выход для рабочего, у которого нет пароля, ссылка протухла или сменился телефон. Заменить в §3.4 шаг 2 «новое приглашение» на это.
- Обработать `#error=…otp_expired` на `/login`: текст «Ссылка устарела. Пришлём новую» + поле почты + «Прислать ссылку».
- В §3.2 шаг 3 записать запрет: UI не вызывает `api/invite.ts` второй раз для того же e-mail. Для Codex — K26: «повторный вызов `api/invite.ts` удаляет существующего пользователя в `catch`; нужна проверка “пользователь уже в этой компании → resend”».
- Всё это тоже упирается в SMTP (HIGH 1). Записать зависимость.

### 2. Список «кого и когда пригласили» из данных не собрать. MED
**Где:** §3.2 шаг 3б («дата из `invite_log.created_at` по совпадению e-mail»), шаг 4 («имя приглашённого и дата приглашения»), §5.2 строка «Владелец видит молчание», §5.3 «Приглашён {имя}, {дата}».
**Что в коде:** в `profiles` нет почты (`000_baseline.sql`: `id, company_id, full_name, role` + `locale`). `auth.users` клиенту недоступна. Значит, связать строку `invite_log` (почта, дата) с человеком (имя) на клиенте нельзя. `invite_log` пишется в `reserve_company_invite` **до** отправки письма: неудачные попытки (`409`, `500`) тоже лежат там как «приглашения». В `invite_log` нет `project_id`. Признака «человек вошёл хоть раз» на клиенте нет.
**Что увижу я:** «Приглашён Андрей, 12.11» — где дата может быть от неудачной попытки или от приглашения на другой объект. Я не отличу «не открыл письмо» от «вошёл, но не отчитался» и позвоню не с тем вопросом.
**Исправить:** в «Людях объекта» показывать только то, что есть: имя и роль из `profiles` + `project_access`. Дату и почту показывать только из ответа `api/invite.ts` в текущей сессии. Строки «вошёл / не входил», «дата приглашения» — «ждёт Codex» (K27: `invite_log.project_id`, `invite_log.user_id`, статус отправки; RPC «последний вход участника»). Убрать из §5.2 «**этот PR** (`invite_log.created_at`)».

**Исправить:** в §3.1 шаг 3 после RPC — один необязательный экран «Как называется фирма и как вас зовут» (две строки, «Сохранить», «Позже»); обновление через `profiles.full_name` (грант есть в `001`) и — для имени компании — «ждёт Codex» (политики `update` на `companies` нет). ### 4. (перенос р1 п.15) Пауза есть, но что она меняет — не сказано. MED

### 6. Автоповтор черновика создаёт двойной отчёт, и он засчитывается в активацию. MED
**Где:** §3.4 «Состояния отправки» п.4 («защита от повтора … не создаёт дубль»), п.3а, п.5; §2.1.
**Что в коде:** `submit_stage_report` ищет повтор только за 10 минут. Сценарий: ответ RPC потерялся на плохой сети, отчёт уже записан. Черновик остался, страницу закрыли. Завтра при открытии черновик уходит сам: `new_percent` = текущему (50 = 50), фото есть → проверки проходят → второй `stage_reports` «50% → 50%» и вторая строка `photos` с тем же путём. Запрос активации §2.1 посчитает это вторым отчётом рабочего. Ещё случай: черновик «станет 50%» посчитан от 40%, а бригадир уже поставил 60% → черновик становится снижением без причины → `comment_required_for_decrease`, черновик висит вечно.
**Исправить:** в §3.4 п.4 записать: перед повтором старше 10 минут UI читает `stage_reports` по `reporter_id = я`, этапу и пути фото (`photos.storage_path`, доступно по RLS). Нашлось — черновик удаляется, показывается «Отправлено ✓». В черновике хранить «было» и «станет»; если текущий % этапа ≠ «было», не отправлять автоматически, а показать «Этап уже {N}%. Отправить фото с {N}%?». В §2.1 исключить отчёты с `old_percent = new_percent` и повторяющимся `storage_path`.

### 7. Окно активации и красная шкала наказывают объект, заведённый заранее. MED

До приглашения — серое «Никто не приглашён», без счёта дней. Записать в §7 вопрос владельцу: окно от создания объекта или от первого приглашения.
