## HIGH

### 1. До шлюза «почта» главная кнопка дня 0 ведёт на экран, которого нет. HIGH
**Где:** §4 «Обзор, никто не приглашён» («до шлюза — экран сопровождения, §0.3»), §5.3 строка «Объект создан, никого нет», §0.3 последний абзац («Запасной путь… — **ждёт владельца**»), §8 п.1, §8 п.17.
**Что в документе:** главное действие — «Пригласить рабочего». До шлюза оно ведёт на «экран сопровождения». Содержание этого экрана не описано: кто сопровождает и где клиент об этом узнаёт — «ждёт владельца». Контакт показывается «только если `legal.ts` заполнен» (§8 п.17), а `legal.ts` сейчас пуст.
**Что увижу я:** регистрируюсь, завожу объект, жму единственную жёлтую кнопку. Попадаю на экран без кнопки, без телефона, без почты. Это ровно тупик дня 0 из раунда 1, только переименованный. Плюс §3.2 шаг 4 сразу начинает желтеть «Никто не приглашён · 3 дня» (см. MED 4).
**Почему HIGH, а не «ждёт владельца»:** решение владельца — кто сопровождает. А что показывает UI, пока владелец не решил, — задача этого PR. Её нет.
**Исправить:**
- В §4 и §8 п.1 описать состояние «шлюз закрыт» как отдельную строку экрана. Признак — переменная сборки (например `VITE_EMAIL_GATE_OPEN`), не ручная правка текста.
- При закрытом шлюзе кнопки «Пригласить рабочего» нет. Главное действие обзора — «Отметить первый этап» (оно работает сегодня). Под ним одна строка: «Приглашение рабочих по почте включим после проверки доставки писем». Если `legal.ts` заполнен — «Хотите начать раньше — {телефон}, поможем завести бригаду».
- Без заполненного `legal.ts` и без шлюза — рекомендация в §7 п.2 одной фразой: самостоятельную регистрацию не открываем. Сейчас там «или», и оба варианта без UI.
- В §5.3 строку «Объект создан, никого нет» разбить на «шлюз открыт» и «шлюз закрыт».

### 2. Тот же рабочий на второй объект: документ отправляет владельца в ссылку для входа, а рабочий войдёт и объекта не увидит. HIGH
**Где:** §3.2 шаг 3 (проверка «человек уже в «Людях объекта» → … «Отправить ссылку для входа»» и текст `409`: «Этот адрес уже есть в BuildProof. Если это ваш рабочий — отправьте ссылку для входа»), §8 п.5, §0.3 «Повторная ссылка от владельца».
**Что в коде:** `api/invite.ts` для уже существующего адреса отвечает `409 email_unavailable` (ветка `already` / `422` / пустые `identities`) и доступ к новому объекту **не создаёт**. Проверка «уже в Людях объекта» в документе смотрит только этот объект. Сопоставить строку по почте UI не может: в `profiles` почты нет (`000_baseline.sql`). При этом выдать доступ существующему человеку уже можно: политика `project_access_insert` для `gc` есть (`001_security_and_profile_locale.sql:13`), переключатель — на `/project/:id/settings` (§0.2).
**Что увижу я:** бригада закончила крышу в Элве, завожу объект в Тарту, ввожу тех же двух рабочих. Получаю `409` и совет «отправьте ссылку для входа». Отправляю. Рабочие входят, видят только Элву. Я думаю, что всё сделал, а через три дня у меня жёлтое «отчётов нет». Это мой обычный случай: бригада одна, объекты меняются. Если адрес принадлежит человеку **другой** фирмы, ссылка вообще ведёт его в чужой кабинет.
**Исправить:**
- На экране приглашения над строками «Имя + почта» поставить блок «Уже работают у вас» — люди компании без доступа к этому объекту (`profiles` компании минус `project_access` объекта). У каждого строка «Добавить на объект» (вставка в `project_access`, есть сегодня, шлюз «почта» не нужен). Для второго объекта это главное действие, а не форма почты.
- Текст `409` заменить: «Этот адрес уже занят. Если человек уже работает у вас — добавьте его из списка «Уже работают у вас». Если нет — нужен другой адрес». «Отправить ссылку для входа» из текста `409` убрать: она не даёт доступа.
- В §8 п.5 записать: «Отправить ссылку для входа» — только для человека, который **уже** есть в «Людях этого объекта».
- Плюс: этот блок работает до шлюза, значит закрывает часть HIGH 1 для фирм, где люди уже заведены.

## MED

### 1. «Отправить ссылку для входа»: владелец вводит почту по памяти, а ответы `signInWithOtp` не описаны. MED
**Где:** §0.3 «Повторная ссылка от владельца», §3.2 шаги 3б, 3в, §4 «Люди объекта», «Обзор, есть отчёты».
**Почему:** с `shouldCreateUser: false` на незнакомый адрес Supabase отвечает ошибкой (регистрация через OTP запрещена), а на частые запросы — лимитом отправки (`over_email_send_rate_limit`, не чаще раза в минуту на адрес). В таблице ошибок §3.4 есть только коды `submit_stage_report`. Почты в `profiles` нет, значит я каждый раз набираю её заново и легко ошибаюсь на одну букву.
**Исправить:** в §3.2 шаг 3б добавить таблицу состояний «Отправить ссылку для входа»: успех — «Ссылка отправлена на {почта}. Если {имя} не видит письмо — пусть проверит «Спам»»; адрес не найден — «Такого адреса нет в BuildProof. Проверьте написание или пригласите заново»; лимит — «Повторить можно через минуту» с таймером на кнопке; сеть — «Не отправлено, попробуйте ещё раз». Поле почты на устройстве владельца предзаполнять адресом из ответа приглашения, если он сохранён локально (IndexedDB, только как удобство; при пустом — пустое поле). Для Codex добавить в K27: отдавать владельцу почту своих участников.

### 2. Главное действие «Обзор, есть отчёты» требует данных, которых у владельца нет. MED
**Где:** §4 «Обзор, есть отчёты» («3+ дня без отчёта → «Отправить ссылку для входа» молчащему»).
**Почему:** молчание рабочего три дня чаще значит «не было работы» или «уехал на другой объект», чем «потерял вход». Главная кнопка отправляет письмо и требует почту, которую я не помню (MED 1). Я нажму, напишу почту с ошибкой и решу, что продукт сломан. Признака «вошёл» нет (K27), поэтому UI не знает, что проблема во входе.
**Исправить:** главное действие для 3+ дней молчания — открыть строку человека в «Людях объекта» с текстом «{имя}: последний отчёт {дата}». Там вторично «Отправить ссылку для входа» и подсказка «Если {имя} не может войти». Главным действием обзора оставить «открыть последний отчёт».

### 3. Исправление «адрес набран с ошибкой» оставляет в фирме двойника, которого не удалить. MED
**Где:** §3.2 шаг 3в («убрать человека с объекта (переключатель доступа) и пригласить по правильному адресу»).
**Что в коде:** `api/invite.ts` при первом приглашении уже создал пользователя `auth.users` и строку `profiles` с `company_id` фирмы. Переключатель снимает только `project_access`. Удаления человека из фирмы в UI и в политиках нет.
**Что увижу я:** в списке людей фирмы два «Андрея», один мёртвый. Через месяц на новом объекте выберу не того (особенно после исправления HIGH 2, где список «Уже работают у вас» станет главным путём).
**Исправить:** в §3.2 шаг 3в записать: строку с ошибочным адресом помечать в UI как «адрес с ошибкой, не использовать» нельзя (нет поля) — поэтому при повторном приглашении того же имени подсказывать «У вас уже есть {имя} без доступа к объектам — это он?». Для Codex — K33: удаление/отключение участника компании владельцем (`profiles` без доступа к объектам → скрыть или удалить через `api/`).

### 4. Жёлтое «Никто не приглашён · N дней» горит, когда приглашать нечем. MED
**Где:** §3.2 шаг 4, §8 п.15 («Никто не приглашён»: ▲ жёлтое с 3-го), §5.3.
**Почему:** счёт идёт от `projects.created_at`. До шлюза «почта» (HIGH 1) пригласить нельзя, но объект желтеет и встаёт наверх «хуже по свежести» (§3.2 шаг 5). Объект, заведённый за две недели до выхода бригады, жёлтый 11 дней. Предупреждение, на которое нельзя ответить действием, я через неделю перестану читать — и пропущу настоящее.
**Исправить:** при закрытом шлюзе «Никто не приглашён» — всегда серое, без счёта дней и без подъёма в списке. При открытом — жёлтое с 3-го дня оставить, но с главным действием в той же карточке («Пригласить рабочего»). Для «приглашены, отчётов нет» оставить текст «объект создан N дней назад» и не поднимать объект выше объектов с реальным простоем (7+ дней после отчёта).

### 5. Отчёты на паузе принимаются и тонут внизу списка. MED
**Где:** §3.2 шаг 9 («объект не краснеет… уходит в группу ниже активных… Сервер продолжает принимать отчёты»), §0.1 `projects.status`.
**Почему:** если рабочий отчитался по объекту на паузе, значит, работа идёт, а я об этом не знаю (поставил паузу и забыл, или бригада вышла раньше). Документ прячет такой отчёт: объект без цвета и в нижней группе.
**Исправить:** в §3.2 шаг 9: если у объекта на паузе есть отчёт после даты паузы (до Codex — после последнего изменения статуса не известно, поэтому: любой отчёт за последние 7 дней), чип «На паузе · новый отчёт {дата}» и главное действие карточки «Вернуть в работу». То же для «Завершён».

### 6. Владелец, забывший пароль до шлюза, заперт без контакта. MED
**Где:** §3.2 шаг 1, §4 «Забыли пароль» (шлюз «почта»), §8 п.17 (контакт только из заполненного `legal.ts`).
**Почему:** это платящий человек (ранг Б). До шлюза «Забыли пароль?» не работает, а контакт скрыт. Выхода нет совсем. Сейчас документ говорит только, что ссылка включается после шлюза, — но не что видно вместо неё.
**Исправить:** в §4 «Вход» при закрытом шлюзе показывать «Забыли пароль?» как текст: «Восстановление по почте скоро включим. {контакт из `legal.ts`}». При пустом `legal.ts` — это ещё один довод в §7 п.2 не открывать регистрацию. Записать оба состояния строкой в §4.

### 7. Контракт ссылки заказчика: токен показывается один раз, а потерять его — дело минуты. MED
**Где:** `docs/contracts/client-links.md` §1 `token` («Shown to the owner once»), §4 («Создать ссылку (copy / WhatsApp)»).
**Почему:** я скопирую ссылку, отправлю заказчику в WhatsApp, а через месяц он скажет «потерял». По контракту показать её снова нельзя, нужно создать новую. Но `first_opened_at` и «Успех» (§3) привязаны к ссылке: новая ссылка без открытия, старая не отозвана — метрика «объект закрыт с открытой ссылкой» начинает считать мусор, а в моём списке копятся неотличимые ссылки.
**Исправить:** в §4 контракта описать «Ссылка потеряна»: действие «Новая ссылка взамен» создаёт ссылку и **сразу** отзывает старую (один вызов или два подряд в UI с одним подтверждением). В §1 `label` сделать обязательным для UI. В §3 уточнить: «Успех» считает любую неотозванную открытую ссылку, а замена не сбрасывает факт открытия старой — либо записать, что это решает Codex.
