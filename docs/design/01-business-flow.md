### 0.3. Может ли рабочий сегодня дойти до отчёта

**В текущем UI — нет.** Приглашения из UI нет. Главная кнопка рабочего заканчивается ошибкой `forbidden`.

**После этого PR — только когда пройден шлюз выпуска «почта» [О2-2, М2-1, И2-2].** Без своего SMTP стандартная почта Supabase шлёт письма только на адреса участников проекта Supabase. На почту рабочего письмо не придёт. Поэтому путь по почте **не готов** и в документах не называется готовым, пока на стенде не проверено:
1. Свой SMTP подключён. Письмо приглашения и письмо входа доходят на внешние адреса (Gmail, Outlook, mail.ee).
2. Ссылка из письма открывает `/project/:id/today` у рабочего с одним объектом.
3. На Vercel заданы переменные `api/invite.ts` (`SITE_URL`, `SUPABASE_SERVICE_ROLE_KEY` и др.).

Запись о проверке — в `test-log.md`. Кто и когда подключает SMTP — **ждёт владельца**, это блокер ранга А.

Что работает после шлюза:
- **Приглашение:** `api/invite.ts` (`worker`, этот объект) → письмо → сессия (`detectSessionInUrl: true`) → `/dashboard` → `today`.
- **Повторный вход и потеря сессии** [О2-1, М2-2, Б2r2-Н1, И2-1]: на `/login` кнопка «Войти по ссылке на почту». Она вызывает `signInWithOtp({ email, options: { shouldCreateUser: false, emailRedirectTo: SITE_URL + '/login' } })`. Сессия теряется часто:
  - письмо открылось во встроенном браузере почты;
  - значок на главном экране iOS хранит данные отдельно от Safari;
  - Safari стирает данные сайта после 7 дней без захода.
- **Повторная ссылка от владельца:** «Отправить ссылку для входа ещё раз» — тот же `signInWithOtp` на почту, которую владелец вводит заново (в `profiles` почты нет). `api/invite.ts` второй раз для того же человека **не вызывается**: повторный вызов возвращает `409` или удаляет уже приглашённого пользователя вместе с доступом (K26).
- **Просроченная ссылка:** `#error=access_denied&error_code=otp_expired` на `/login` → экран «Ссылка устарела. Пришлём новую» с полем почты и кнопкой «Отправить новую ссылку».

Что не работает:
- **Рабочий без почты.** Пути нет до C3 (`worker_links`) [О2-2, Б2r2-М6]. UI не принимает адрес самого владельца в строке приглашения: он должен отличаться от почты текущего пользователя. Подпись поля: «Почта рабочего, которую он открывает на телефоне».
- **Подсказка «Добавьте на главный экран».** На iOS не показываем, пока на стенде не проверено, что сессия переживает переход [Б2r2-Н1].
- **Код из письма** (6 цифр, `verifyOtp`, вводится в любом браузере) — **ждёт Codex/владельца** (шаблон письма).

Запасной путь для первых фирм до шлюза — **ждёт владельца** [О2-2, И2-2]. Основатель сам сопровождает клиента: заводит рабочих и проверяет, что вход работает. Кто это делает и где клиент об этом узнаёт, решает владелец. Альтернатива — не открывать самостоятельную регистрацию до шлюза.

## 2. Метрики

### 2.1. Активация [О2-12, О2-14, И2-4, И2-5, М2-7]

`decisions.md` §4: объект с ≥ 3 отчётами рабочих за 7 дней.

- **Отчёт рабочего** — событие от автора с ролью `worker`. Бригадир и владелец **не считаются** — решение оркестратора [О2-14], вопрос из §7 снят. Роль — один параметр запроса.
- **Что считается событием:**
  - строка `stage_reports`;
  - или фото рабочего без отчёта (`photos.report_id is null`);
  - события **одного автора** в пределах 10 минут от его предыдущего события — один отчёт.
- **Не считаем:**
  - возвращённые (когда появится статус);
  - повторы: `stage_reports`, фото которого уже было в более раннем отчёте с тем же `storage_path` [М2-6];
  - отчёты владельца и бригадира.
- **Окно:** 7 суток от первого успешного приглашения рабочего на объект. По текущим данным это приближение: самый ранний `auth.users.created_at` среди рабочих с `project_access` к объекту (пользователь создаётся в момент приглашения). Если рабочих нет — от `projects.created_at`.
- **Оговорки:**
  - рабочего, приглашённого раньше на другой объект, этот способ датирует первым приглашением;
  - роль берётся текущая;
  - статусов и пометки повторов в БД нет.
  - Точное окно — после K28 (`project_access.created_at`).

Запрос для владельца продукта: SQL Editor Supabase, под сервисной ролью. RLS под пользователем отрежет чужие компании. Это не аналитика в продукте.

```sql
-- активация по всем объектам (приближение); запускать в SQL Editor Supabase (сервисная роль)
with w as (select id from public.profiles where role in ('worker')),           -- роль — один параметр
start as (                                                                       -- начало окна
  select p.id as project_id, p.company_id,
         coalesce(min(u.created_at), p.created_at) as t0
  from public.projects p
  left join public.project_access a on a.project_id = p.id and a.user_id in (select id from w)
  left join auth.users u on u.id = a.user_id
  group by p.id, p.company_id, p.created_at
),
rep as (                                                                         -- отчёты без повторов фото
  select sr.project_id, sr.reporter_id as who, sr.created_at as at
  from public.stage_reports sr
  where sr.reporter_id in (select id from w)
    and not exists (
      select 1 from public.photos ph
      join public.photos ph0 on ph0.storage_path = ph.storage_path and ph0.report_id is not null
      join public.stage_reports sr0 on sr0.id = ph0.report_id and sr0.created_at < sr.created_at
      where ph.report_id = sr.id)
  union all
  select ph.project_id, ph.uploaded_by, ph.uploaded_at
  from public.photos ph where ph.report_id is null and ph.uploaded_by in (select id from w)
),
win as (
  select r.*, s.company_id from rep r join start s on s.project_id = r.project_id
  where r.at >= s.t0 and r.at < s.t0 + interval '7 days'
),
g as (
  select project_id, company_id,
    case when lag(at) over (partition by project_id, who order by at) > at - interval '10 minutes'
         then 0 else 1 end as is_new
  from win
)
select s.company_id, s.project_id, s.t0 as window_start,
       coalesce(sum(g.is_new), 0) as worker_reports_7d,
       coalesce(sum(g.is_new), 0) >= 3 as activated
from start s left join g on g.project_id = s.project_id
group by s.company_id, s.project_id, s.t0
order by s.company_id;
```

Подтверждение крупного скачка — одно касание [Б2-9, О2-6, Б2r2-М4]:
- **Строка очереди** (высота ≥ 120 px) показывает превью фото, «было → заявлено» и имя.
- **Кнопки:** «Подтвердить» и «Вернуть» на разных краях строки, между ними ≥ 16 px.

Отмены на сервере нет: RPC проверки ещё нет вовсе, отмену в контракте `reports.md` никто не предусмотрел. Поэтому запрос уходит **после** 5 секунд. «Отменить» в это окно запрос не отправляет. ### 3.4. Рабочий

#### Экран отчёта (один для всех ролей; подпись главной кнопки — «Отчитаться»)

- **Вход в отчёт** [Б2r2-М3]: на `today` главная кнопка «Сфотографировать: {этап}» сразу открывает камеру. Лист отчёта открывается после снимка. Отдельного касания «Отчитаться» нет.
- **Шапка:** объект и адрес крупно, имя рабочего.
- **Этап** выбран заранее: последний этап этого человека, иначе этап его открытой задачи, иначе первый незавершённый. Смена этапа — кнопки ≥ 48 px, без `<select>`.
- **Фото:** `<input type="file" accept="image/*" capture="environment">`; вторично «Выбрать из галереи».
- **%** — один набор для приложения и лендинга [О2-14, И2-6]: «−10», «+10», «+25», «Готово 100%», все ≥ 48 px.
  - По умолчанию «без изменений», поэтому «Отправить» активна сразу после снимка (только фото) [Б2r2-L2].
  - Значения ограничены 0 и 100. Кнопка неактивна, если шаг выводит за край. «Готово 100%» показывает «станет 100% — этап готов» [Б2r2-L3].
  - На экране «было N% → станет M%». Ползунка и автосохранения нет.
  - Лендинг-PR меняет `phone.all` («Всё») и текст `how.steps[0]` на этот набор.
- **Снижение %:** причина одним касанием («переделка» / «ошибка в учёте» / «снос»). Текст причины уходит в `p_comment`.
- **Скачок > 25:** обычный текст ≥ 17 px, контраст ≥ 7:1, не серый: «Большой шаг. Владелец посмотрит фото» [Б2r2-L1].
- **Закрытие задачи** со связанным этапом открывает этот же экран.

#### Черновик и отправка [О2-3, О2-4, О2-5, О2-7, Б2r2-Н2, Б2r2-М1, Б2r2-М2, Б2r2-М5, М2-6]

**Хранение.**
- Черновики лежат в **IndexedDB**, по одной записи на черновик (не на этап).
- Поля записи:
  - `draftId` (uuid, создаётся на телефоне);
  - `projectId`, `stageId`;
  - `seenPercent` — какой % этапа видел рабочий;
  - `newPercent` — абсолютный %, а не «+10»;
  - `reason`;
  - фото как `Blob`;
  - `storagePath`;
  - `createdAt`, `attempts`, `lastAttemptAt`, `state`.
- Ограничения:
  - `navigator.storage.persist()` запрашивается;
  - не больше 10 черновиков (**цель**). При 8 — «На телефоне 8 неотправленных отчётов. Найдите сеть»; при 10 — новый снимок не сохраняется, текст объясняет почему;
  - хранилище сессии Supabase в `localStorage` **не трогаем**: никаких фото и черновиков там.

**Путь фото** создаётся один раз, при сохранении черновика: `{projectId}/{stageId}/{draftId}.jpg`. Загрузка идёт с `upsert: false`: политики `update` на хранилище нет, поэтому `upsert: true` на существующий путь не сработает. Ответ «файл уже существует» на свой путь считается успехом. При ошибке RPC файл не удаляется, пока жив черновик (в отличие от `photos.ts:85–89`).

**Отправка (порядок):**
1. Черновик записан в IndexedDB **до** первой попытки.
2. Загрузка фото по `storagePath`.
3. **Проверка перед каждым повтором:** `select report_id from photos where storage_path = :path` (RLS `photos_select` разрешает). Если строка с `report_id` нашлась → «Отправлено ✓ (дошло раньше)», черновик удаляется, RPC не вызывается. Это защита от дублей, пока нет `client_request_id` (K29).
4. **Проверка устаревания:** текущий % этапа ≠ `seenPercent` → не отправлять автоматически. Состояние черновика «Не принято: этап уже N%», кнопки «Отправить с новым %» (открывает лист с текущим значением) и «Удалить».
5. Вызов `submit_stage_report(stageId, newPercent, reason, [storagePath])`.

**Ответ не пришёл за 20 с (цель):**
- экран пишет «Проверяем, дошёл ли отчёт» и выполняет проверку шага 3;
- «Не отправлено» пишем только когда известно, что отчёт не дошёл.

**Автоповтор** [Б2-11, О2-5]:
- срабатывает, пока страница открыта: по `online`, по `visibilitychange` → `visible` и `focus`, по таймеру 15 с / 30 с / 60 с / раз в 2 мин (**цель**);
- через 30 мин таймер останавливается, повтор ждёт `online` или возврата на страницу [Б2r2-L4];
- одновременно идёт одна попытка;
- «Отправить снова» остаётся запасной кнопкой;
- из закрытой или замороженной страницы ничего не уходит.
- Текст в приложении: «Отправим, когда появится сеть, пока страница открыта». На лендинге этот текст повторяем **только после теста в режиме полёта на iPhone** с записью в `test-log.md` — **ждёт владельца** [И2-11].

**Плашка «Не отправлено»** [О2-7, Б2r2-М5]:
- свой токен предупреждения, **не жёлтый цвет главной кнопки**;
- SVG-значок формы;
- текст ≥ 17 px, контраст ≥ 7:1;
- строки: «Не отправлено: {N} отчёт(а)», «Последний снимок {время}», статус «Пробуем снова… последняя попытка {время}» или «Ждём сеть»;
- под плашкой — единственная жёлтая кнопка «Отправить снова». Во время попытки она показывает «Отправляется» и не исчезает.

**После успеха:** «Отправлено ✓», миниатюра, этап, «было → стало», время. «Ещё отчёт» — вторично. Черновик удаляется.

5. Гарантия «если рабочие не начнут».
6. K9: видит ли заказчик «принято» или только «проверено ✓».
7. Счётчик «N из 3 отчётов за 7 дней» на обзоре.
8. Активация: окно от создания объекта или от первого приглашения (сейчас — от приглашения, с приближением §2.1) [М2-7]. Нужно ли правило «в разные дни».

10. Оплата: способ первой оплаты; от какой даты считать 30 дней — от аккаунта (лендинг) или от объекта (`pricing.ts`) [М2-1].

12. Фактические цифры («уже N объектов»).
13. K16: в демо лендинга 7 дней красным или 5 дней жёлтым (`decisions.md` §1 п.2 против §5.5) [И2-L13].

## 8. Решения для design-brief

1. **Шлюз выпуска «почта».** «Пригласить рабочего», «Войти по ссылке на почту», «Забыли пароль?» и «Отправить ссылку для входа» включаются в продакшене только после проверки на стенде:
   - свой SMTP;
   - письмо доходит на Gmail, Outlook, mail.ee;
   - ссылка ведёт в `today`;
   - на Vercel заданы переменные `api/invite.ts`.

   Запись — в `test-log.md`. До шлюза путь по почте нигде не называется готовым. Первые фирмы — сопровождение основателем (ждёт владельца) [О2-2].
2. Экран отчёта вызывает `submit_stage_report` (K14).
3. **RPC компании** — на `/dashboard`, когда сессия есть, а профиля нет. `ProfileNotConfigured` — только при ошибке. Домен почты как имя компании не показываем [О2-11].
4. **День 0:** главное действие — «Пригласить рабочего». Несколько строк «Имя + почта», одна отправка, `api/invite.ts` по разу на строку. Почта ≠ почта владельца. Итог: «Письмо отправлено на {почта}…», а не «приглашён» [Б2-10, М2-1].
5. **`api/invite.ts` второй раз на того же человека не вызываем.** Повтор — «Отправить ссылку для входа» (`signInWithOtp`, `shouldCreateUser: false`). `409` → «уже есть в BuildProof — отправить ссылку для входа?». K26 передан Codex [О2-1].
6. **`/login`:** «Войти по ссылке на почту». `otp_expired` / `access_denied` из адреса → «Ссылка устарела» + «Отправить новую ссылку». Подсказку «Добавьте на главный экран» на iOS не показываем до проверки.
7. **«Люди объекта»** строятся из `project_access` + `profiles`. Статус — только «приглашён». Признак «вошёл» — K27 [О2-15].
8. **Фирма без бригадира** — основной случай. С бригадиром владелец проверяет только отчёты старше 48 ч.
9. **Проверка — одно касание** в строке очереди:
   - превью обязательно до активации кнопки;
   - 5 с «Отменить», запрос уходит после окна (отмены на сервере нет);
   - «Подтвердить все мелкие (N)» без скачков > 25;
   - автор скачка его не подтверждает [О2-6, Б2-9].
10. **Черновики:**
    - IndexedDB, запись на черновик, `draftId` = uuid, не больше 10 (цель);
    - путь фото `{projectId}/{stageId}/{draftId}.jpg`, `upsert: false`, «уже существует» = успех;
    - перед повтором — проверка по `storage_path`;
    - устаревший этап → «Не принято: этап уже N%» + «Отправить с новым %» / «Удалить»;
    - для каждого кода RPC — своё состояние (§3.4);
    - `localStorage` сессии не трогаем [О2-3, О2-4].
11. **Автоповтор** пока страница открыта: `online`, возврат на страницу, таймер, стоп через 30 мин. Текст: «Отправим, когда появится сеть, пока страница открыта». Лендинг повторяет его только после теста на iPhone [О2-5].
12. **Плашка «Не отправлено»:**
    - свой токен предупреждения, не жёлтый главной кнопки;
    - SVG-значок, число черновиков, статус повтора;
    - AAA [О2-7].
13. **Бюджет касаний — от значка:** 6 для отчёта с %, 5 для фото (цель). Сейчас: % невозможен, фото — 10. Камера открывается прямо с `today` [О2-8].
14. **Кнопки % одни для приложения и лендинга:** «−10», «+10», «+25», «Готово 100%», ≥ 48 px, в пределах 0–100, по умолчанию «без изменений». Лендинг-PR правит `phone.all` и `how.steps[0]` [О2-14].
15. **Свежесть:**
    - шкала: сегодня / 1–2 / 3–6 / 7+ дней;
    - «Никто не приглашён»: серое 0–2 дня, ▲ жёлтое с 3-го;
    - «приглашены, отчётов нет»: ▲ жёлтое с 3-го дня, без красного до K28;
    - пауза и завершённые: без цвета свежести, ниже активных, чип «На паузе» / «Завершён» [О2-10].
16. **Тариф:**
    - главное действие — «Написать о продолжении», только если `legal.ts` заполнен;
    - даты конца пробного периода нет;
    - «только чтение» и «напоминание за 5 дней» из текста приложения убираем [О2-9].
17. **Контакты в тупиках** показываем только из заполненного `legal.ts` (`LEGAL.phone`, `LEGAL.email`, срок `hero.humanTail`). Иначе скрываем [О2-11].
18. **Активация:** только `worker`; окно от первого приглашения (приближение, §2.1); повторы по `storage_path` исключены; считает запрос §2.1 [О2-12, О2-14].
19. **Статусы:** до K15 в продакшене всё «Принято». На ленте пометка «крупный скачок +N, не проверен». «Ждёт проверки ○» и «Проверено ✓» — только на заглушках.
20. **Роли в тексте:** «Владелец», «Бригадир», «Рабочий», «Заказчик». «Почта», не «Email». Сервер не отдаёт видимых строк.
21. **Обещания без продукта (§9)** в приложении не повторяем. Лендинг-PR вычищает их.
