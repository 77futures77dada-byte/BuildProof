## 2. Метрики

### 2.1. Активация

- **Что считаем:** ≥ 3 отчёта рабочих (`role = 'worker'`) за 7 суток. Бригадир и владелец не считаются.
- **Отчёт** — строка `stage_reports` или фото рабочего без отчёта. События одного автора в пределах 10 минут — один отчёт. Повторы по `storage_path` исключены.
- **Окно** начинается в `t0 = greatest(min(auth.users.created_at) рабочих с доступом, projects.created_at)` [О3-12, И3-1]. Для рабочего, уже бывшего в системе, окно не раньше создания объекта. Точно — после K28.
- **Где считаем:** SQL Editor Supabase (сервисная роль), не аналитика в продукте.

```sql
with w as (select id from public.profiles where role in ('worker')),
start as (
  select p.id as project_id, p.company_id,
         greatest(coalesce(min(u.created_at), p.created_at), p.created_at) as t0
  from public.projects p
  left join public.project_access a on a.project_id = p.id and a.user_id in (select id from w)
  left join auth.users u on u.id = a.user_id
  group by p.id, p.company_id, p.created_at
),
rep as (
  select sr.project_id, sr.reporter_id as who, sr.created_at as at
  from public.stage_reports sr
  where sr.reporter_id in (select id from w)
    and not exists (
      select 1 from public.photos ph
      join public.photos ph0 on ph0.storage_path = ph.storage_path and ph0.report_id is not null
      join public.stage_reports sr0 on sr0.id = ph0.report_id and sr0.created_at < sr.created_at
      where ph.report_id = sr.id)
  union all
  select ph.project_id, ph.uploaded_by, ph.uploaded_at
  from public.photos ph where ph.report_id is null and ph.uploaded_by in (select id from w)
),
win as (
  select r.*, s.company_id from rep r join start s on s.project_id = r.project_id
  where r.at >= s.t0 and r.at < s.t0 + interval '7 days'
),
g as (
  select project_id, company_id,
    case when lag(at) over (partition by project_id, who order by at) > at - interval '10 minutes'
         then 0 else 1 end as is_new
  from win
)
select s.company_id, s.project_id, s.t0 as window_start,
       coalesce(sum(g.is_new), 0) as worker_reports_7d,
       coalesce(sum(g.is_new), 0) >= 3 as activated
from start s left join g on g.project_id = s.project_id
group by s.company_id, s.project_id, s.t0
order by s.company_id;
```

### 2.2. Успех, удержание, оплата

- **Успех:** объект `completed`, у которого есть хотя бы одна неотозванная ссылка заказчика, открытая хотя бы раз. Считается по объекту, а не по токену (`client-links.md` §3) [О3-14].
- **Удержание:** объекты с ≥ 1 отчётом рабочего за неделю.
- **Оплата:** не считается, биллинга нет.

- **Строка** ≥ 120 px: превью, «было → заявлено», имя. «Подтвердить» неактивна до загрузки превью. «Подтвердить» и «Вернуть» на разных краях, между ними ≥ 16 px.

- **Отправка:** запрос уходит по истечении окна (отмены на сервере нет, K32). Уход с экрана очереди отправляет ждущие подтверждения сразу. Закрытие страницы — не отправляет; при следующем открытии строка снова в очереди с текстом «Не подтверждено: страница закрылась раньше».

### 3.4. Рабочий

#### Экран отчёта

- **Камера сразу:** на `today` главная кнопка «Сфотографировать: {этап}» (`capture="environment"`; вторично «Из галереи»). Лист открывается после снимка.
- **Порядок на листе** (фиксирован, UI-этап добавит DOM-проверку) [О3-10, Б3-М8]:
  1. объект и имя — одна строка;
  2. миниатюра ≤ 25 % высоты;
  3. «было N% → станет M%»;
  4. кнопки «−10», «+10», «+25», «Готово 100%» (≥ 48 px, в пределах 0–100, по умолчанию «без изменений»);
  5. «Этап: {имя} · Сменить»;
  6. причины — только при снижении;
  7. плашки паузы и черновиков — по одной строке.
- **«Отправить»** закреплена внизу (`position: sticky`, ≥ 56 px, с отступом безопасной зоны). Видна без прокрутки на 360 × 640 и 375 × 667 во всех состояниях: рост, снижение, пауза, скачок.
- **Скачок > 25:** «Большой шаг. Владелец посмотрит фото», ≥ 17 px, контраст ≥ 7:1.
- **Закрытие задачи** с этапом открывает этот же экран.

#### Бюджет касаний (цель, от значка)

| Сценарий | Цель | Сейчас |
|---|---|---|
| Отчёт с % | значок → «Сфотографировать» → затвор → «Использовать фото» → «+10» → «Отправить» = 6 | невозможен |
| Только фото | 5 | 10 |
| 2+ объекта / другой этап / снижение | +1 каждое | — |
| Вход снова (код) | «Прислать код на p•••» → почта → письмо → ввод 6 цифр (автоподстановка кода на iOS/Android, где есть) → «Войти» ≈ 5 (цель) [Б3-М5] | — |

#### Черновики [О3-7, Б3-М1..М4]

**Запись в IndexedDB** — одна на черновик:
- `draftId` (uuid), `userId`, `projectId`, `stageId`;
- `seenPercent`, `newPercent` (абсолютный), `reason`;
- фото `Blob`, `storagePath = {projectId}/{stageId}/{draftId}.jpg`;
- `state`: `editing` / `queued` / `unknown` / `stale` / `sent`;
- `createdAt`, `attempts`, `lastAttemptAt`.

`navigator.storage.persist()` запрашиваем. `localStorage` сессии не трогаем.

**Правила:**
1. **Сохраняется сразу после снимка** (`onchange` поля фото), `state = editing`. Открыл `today` с `editing` → лист с этим снимком: «Вы не закончили отчёт». `editing` старше 24 ч (цель) → `queued`.
2. **Свои черновики не блокируют друг друга.** Черновики одного этапа уходят по порядку `createdAt`. «Было» на листе учитывает свои неотправленные.
3. **Только фото** (`newPercent = seenPercent`) — разрешено и никогда не устаревает.
4. **Этап уже выше:** текущий % ≥ `newPercent` → отправить фото с текущим % автоматически и написать «Этап уже {N}%. Ваше фото добавлено». Ручное решение («Не принято: этап уже N%» → «Отправить с новым %» / «Удалить») — только если текущий % < `newPercent` и ≠ `seenPercent`.
5. **Чужие черновики.** Автоповтор и «Отправить снова» работают только для `userId` текущего пользователя. Чужие: «На телефоне N отчётов другого человека. Уйдут, когда он войдёт», без «Удалить».
6. **Выход с черновиками:** «N отчётов не отправлены. Они уйдут, только когда вы войдёте снова» — «Остаться» (главное) / «Выйти всё равно».
7. **Лимит 10** считает только неотправленные и мешает **только без сети**: «Телефон хранит не больше 10 отчётов. Отправьте или удалите старые». При сети новый отчёт пробуется сразу.

**Отправка:**
1. Загрузка фото по `storagePath`, `upsert: false`; «файл уже существует» = успех. При ошибке RPC файл не удаляем.
2. Перед повтором — `select report_id from photos where storage_path = :path`. Есть `report_id` → «Отправлено (дошло раньше)», RPC не вызываем (до K29).
3. Правило 4 выше.
4. `submit_stage_report(stageId, newPercent, reason, [storagePath])`.

**Три состояния без успеха** — разная форма значка (SVG; формы — только по таблице `02-type.md` §8, описания ниже ориентировочные), ≥ 17 px, AAA; свой токен предупреждения, не жёлтый главной кнопки:
- `queued` — точно не дошло: «Сохранено на телефоне, не отправлено. Откройте эту страницу, когда появится сеть»;
- `unknown` («?» в круге) — ответа не было 20 с (цель), проверка не прошла: «Нет сети — проверим, когда появится». Анимация не дольше 20 с;
- `stale` — правило 4, ручное решение.

**Плашка:** «Не отправлено: N · Проверяем: M · последний снимок {время} · последняя попытка {время}». Под ней единственная жёлтая кнопка «Отправить снова»; для `unknown` она сначала делает проверку.

**Автоповтор** (механика): по `online`, `visibilitychange`/`focus`, таймер 15 / 30 / 60 с / 2 мин; стоп через 30 мин; одна попытка за раз.

**Текст в приложении** до записи теста на iPhone в режиме полёта в `test-log.md` — только `queued`-текст выше. Фразу «Отправим, когда появится сеть, пока страница открыта» не используем ни в приложении, ни на лендинге до теста [О3-8, И3-4].

**Ошибки RPC** — черновик никогда не удаляется молча:

| Код | Экран | Черновик |
|---|---|---|
| сеть / таймаут | `unknown` → проверка → `queued` | остаётся |
| `authentication_required` | «Войдите в этом браузере — N отчётов ждут» + «Прислать код» | остаётся |
| `forbidden` | «Нет доступа к объекту. Скажите владельцу» | остаётся, «Удалить» вручную |
| `comment_required_for_decrease` | не должен возникать после правила 4; если возник — лист с текущим % | остаётся |
| `photo_required_for_progress` | «Для роста % нужно фото» | остаётся |
| `nothing_to_report` | «Добавьте фото или измените %» | остаётся |
| `invalid_photo_path` | «Фото не загрузилось. Снимите ещё раз» | фото заменяется |
| `invalid_percent` | не возникает (кнопки 0–100) | остаётся |

## 8. Решения для design-brief

1. **Шлюз «почта»** (`VITE_EMAIL_GATE_OPEN`):
   - открывается только по 7 пунктам §0.3 с записью в `test-log.md`;

   - правило выпуска при пустом `legal.ts` — ждёт владельца.
2. Отчёт рабочего — `submit_stage_report`.
3. RPC компании — на `/dashboard` при сессии без профиля.
4. **«Уже работают у вас» → «Добавить на объект»** — главный путь для второго объекта, работает без почты. Текст `409` ведёт туда.
5. **Приглашение** (шлюз открыт): строки «Имя + почта», «Пригласить (N)», `api/invite.ts` по разу на строку. Повторно для того же человека не вызываем. Почта ≠ почта владельца.
6. **Вход:**
   - главный путь — 6-значный код на той же странице (`verifyOtp`, `type: 'email'`); ссылка вторично (`pkce`);

9. **Подтверждение:** одно касание, окно 7 с, плашка вверху списка, один счётчик на несколько, уход с экрана отправляет сразу; «Подтвердить все мелкие (N)» только ≤ 25.
10. **Черновики:**
    - IndexedDB, `userId`, сохранение сразу после снимка;
    - свои не блокируют друг друга; только фото разрешено;
    - этап выше → фото с текущим % автоматически;
    - лимит 10 только неотправленных и только без сети;
    - выход предупреждает;
    - путь фото по `draftId`, `upsert: false`, проверка по `storage_path`.
11. **Состояния:** `queued` / `unknown` («Нет сети — проверим, когда появится») / `stale`. У каждого свой значок; токен предупреждения не жёлтый. Обещание автоотправки не пишем нигде до теста на iPhone.

13. **Бюджет касаний от значка:** 6 / 5 (цель), повторный вход ≈ 5.
14. **Кнопки %** — одни на приложение и лендинг: «−10 / +10 / +25 / Готово 100%».
15. **Свежесть:** шкала сегодня / 1–2 / 3–6 / 7+; без красного «без первого отчёта» до K28. Пауза: без цвета, ниже. Пришёл отчёт → чип «Пришёл отчёт», объект в активных.
