### 0.3. Можно ли сегодня довести рабочего до отчёта

**В текущем UI нельзя.** Приглашения из UI нет: `InviteWorkerLink` шлёт `/login`, у рабочего нет пароля. Главная кнопка рабочего ведёт на `update_stage_progress`, а он рабочему запрещён. Фото без % загрузить можно, но только рабочему, у которого уже есть аккаунт.

**После этого PR можно, на существующем бэкенде.** Шаги:
1. Владелец вызывает `api/invite.ts` с `role: 'worker'` и `project_ids: [объект]`. API создаёт профиль и доступ к объекту.
2. Рабочий получает письмо и открывает ссылку. Supabase ставит сессию (`detectSessionInUrl: true` в `supabaseClient.ts`). `/login` с сессией переходит на `/dashboard`. У рабочего один объект, поэтому дальше открывается `/project/:id/today`.
3. Рабочий отправляет фото и % через `submit_stage_report`. Это разрешено ролью, RLS и политиками хранилища.

Условия, которые нельзя проверить по репозиторию (**ждёт Codex / проверки на стенде**):
- письма Supabase доходят на любые адреса, то есть настроен свой SMTP (`onboarding.md` вопрос 1). Стандартная почта Supabase шлёт мало писем и не на все адреса;
- на Vercel заданы `SITE_URL`, `SUPABASE_SERVICE_ROLE_KEY` и другие переменные для `api/invite.ts`;
- у рабочего есть e-mail, и он открывает письмо в том же браузере, где потом будет отчитываться. Сессия живёт в хранилище этого браузера. Пароля у рабочего нет, поэтому на другом телефоне или после очистки браузера он не войдёт без нового приглашения.

Вывод: путь рабочего на e-mail — **рабочий, но временный**. Целевой путь без почты — `worker_links` (C3).

## 2. Метрики

### 2.1. Активация (точное определение) [О8, И1, М8]

`decisions.md` §4: активация = объект с ≥ 3 отчётами рабочих за 7 дней. Уточняем:

- **Отчёт рабочего** — одно событие от человека с ролью `worker`:
  - строка `stage_reports` с `reporter_id` → `profiles.role = 'worker'` (фото и % вместе — это один отчёт, а не два);
  - либо фото рабочего без отчёта (`photos.report_id is null`). Фото одного автора в пределах 10 минут считаются одним отчётом.
- **Считаем** любой статус, кроме возвращённого, включая будущий «ждёт проверки».
- **Не считаем:**
  - возвращённые (`rejected`, когда статус появится);
  - помеченные как повтор (`duplicate_of`, когда поле появится);
  - отчёты владельца и бригадира.
- **Окно:** первые 7 календарных суток от `projects.created_at`. Не скользящее окно.
- **Приближения сегодня:**
  - роль берётся текущая, а не на момент отчёта;
  - статусов и пометки повторов в БД нет, поэтому их не вычитаем;
  - три отчёта за одну минуту засчитаются. Нужно ли правило «в разные дни» — **ждёт владельца**.

Ручной подсчёт для владельца продукта на первых 5 фирмах. Это запрос к БД, а не аналитика в продукте:

```sql
-- активация одного объекта по текущим таблицам (приближение)
with p as (select id, created_at from public.projects where id = :project_id),
ev as (
  select sr.created_at as at
  from public.stage_reports sr join public.profiles pr on pr.id = sr.reporter_id, p
  where sr.project_id = p.id and pr.role = 'worker'
    and sr.created_at < p.created_at + interval '7 days'
  union
  select distinct to_timestamp(floor(extract(epoch from ph.uploaded_at) / 600) * 600)
  from public.photos ph join public.profiles pr on pr.id = ph.uploaded_by, p
  where ph.project_id = p.id and ph.report_id is null and pr.role = 'worker'
    and ph.uploaded_at < p.created_at + interval '7 days'
)
select count(*) as worker_reports_7d, count(*) >= 3 as activated from ev;
```

`pilot_metrics` для активации не подходит: он считает отчёты всех ролей. Для Codex: добавить фильтр `reporter.role = 'worker'` и окно от `projects.created_at`.

### 2.2. Успех и удержание

- **Успех** (`decisions.md` §4): объект `completed` с открытой ссылкой заказчика. «Открытая» — предлагаем так: не отозвана в момент закрытия и открыта заказчиком хотя бы раз [И11]. Сейчас недостижимо: нет ссылки заказчика и нет способа завершить объект в UI. Контракта ссылки нет — **ждёт Codex** (поля `token`, `expires_at`, `revoked_at`, `first_opened_at` — предложение, не API).
- **Удержание:** недельно активные объекты = объекты с ≥ 1 отчётом рабочего за неделю. Считается тем же запросом с другим окном.
- **Оплата** — ведущий показатель для бизнес-модели. Сейчас его посчитать нельзя: биллинга нет [И9].

### 3.4. Рабочий

Экран отчёта (один для рабочего, бригадира и владельца; подпись кнопки везде одна — «Отчитаться») [О6, Б5–8, Б14, Б19, И12]:

- **Шапка:** название объекта и адрес крупно, имя рабочего [Б17].
- **Этап** выбран заранее: последний, по которому этот человек отчитывался. Если таких нет — этап его открытой задачи, иначе первый незавершённый. Смена этапа — крупные кнопки ≥ 48 px по одной в строку, без `<select>`. Название выбранного этапа видно рядом с «Отправить».
- **Фото:** главная кнопка открывает камеру (`<input type="file" accept="image/*" capture="environment">`). Вторичная ссылка «Выбрать из галереи» — для снимков, сделанных без сети.
- **%:** кнопки «−10», «+10», «+25», «100%», все ≥ 48 px, от текущего значения этапа. Видно «было 40% → станет 50%». Ползунка и автосохранения нет: касание кнопки ничего не отправляет.
- **Снижение %:** причина одним касанием — «переделка» / «ошибка в учёте» / «снос». Текст причины уходит в `p_comment`, это закрывает требование БД `comment_required_for_decrease`.
- **Скачок > 25** — тихая строка: «Крупный скачок: его увидят отдельно». Не «ждёт проверки», пока проверки нет (K15).
- **Отправка** только кнопкой «Отправить»: фото загружается в хранилище, затем `submit_stage_report(stage, %, причина, [путь фото])`.
- **Закрытие задачи** со связанным этапом открывает этот же экран с выбранным этапом, а не отдельную загрузку фото [Б14].

Бюджет касаний (**цель**: ≤ 5 от открытого экрана до «Отправлено ✓»):

| Касание | Действие |
|---|---|
| 1 | «Сфотографировать» |
| 2 | спуск затвора |
| 3 | «Использовать фото» (подтверждение в камере iOS/Android) |
| 4 | «+10» (этап уже выбран) |
| 5 | «Отправить» |

Сейчас, у рабочего с аккаунтом, % отправить невозможно (K14). Только фото: вкладка «Фото» → «Добавить фото» → «Выбрать фото» → «Камера» → затвор → «Использовать» → выбор этапа (2 касания) → «Загрузить». Это 9 касаний, посчитано по `Photos.tsx` / `PhotoUploadForm.tsx`.

Состояния отправки [О5, Б3]. Что делает фронтенд сейчас, без фоновой отправки:
1. **Черновик** (этап, %, причина, сжатое фото как data URL) пишется в `localStorage` с ключом `bp:draft:{projectId}:{stageId}` **до** первой попытки. Каждая запись в `try/catch`. Если фото не влезло в хранилище — плашка «Фото не сохранилось на телефоне, снимите ещё раз». Ввод на экране при этом не теряется.
2. **«Отправляется»** — пока идут загрузка и вызов RPC.
3. **Ошибка** или ответа нет дольше 20 с (**цель**, настраиваемая) → жёлтая плашка «Сохранено на телефоне, не отправлено» и кнопка «Отправить снова». Ввод остаётся на экране и переживает перерисовку. Сейчас при ошибке значение откатывается к старому и ввод теряется (`useProjectStages.ts:101–106`, `StageProgressControl.tsx:65–69`) — это убираем.
4. **Повтор** использует уже загруженный путь фото из черновика. Тогда защита от повтора в `submit_stage_report` (10 минут, тот же набор) не создаёт дубль.
5. **При следующем открытии** страницы черновики показываются первой плашкой с числом, и отправка стартует сама. Пока страница закрыта, ничего не отправляется — так и пишем.
6. **«Отправлено ✓»** — экран показывает, что ушло: миниатюра, этап, «было → стало», время. «Ещё отчёт» — вторичная кнопка [Б18]. Черновик удаляется.
7. **Сервер отказал** (`forbidden`: доступ к объекту сняли) → плашка «Отчёт не принят: нет доступа к объекту. Скажите владельцу». Черновик не удаляется молча.

## 5. Ответы на вопросы критики

### 5.1. Чем это лучше WhatsApp-группы [М17, И6]

Сравниваем честно. Колонка «без отчётов рабочих?» показывает, работает ли польза, если рабочие не отчитываются.

| В WhatsApp-группе | В BuildProof | Статус | Работает без отчётов рабочих? |
|---|---|---|---|
| Видно, кто прислал и когда, но не видно, к какому объекту и этапу фото | Фото привязано к объекту и этапу, фильтр по этапу | есть | нет |
| % не считается, история по этапу не собирается | % по этапам, общий % объекта, история изменений этапа | есть (общий % — простое среднее) | нет |
| Чтобы понять, где стоит работа, надо листать чаты | Свежесть последнего отчёта на карточке объекта | частично: считает и правки владельца (K12); «кто» на карточке нет — даст лента `project_activity` в этом PR | нет |
| Проблема тонет среди фото | Отдельный список проблем с приоритетом | есть | **да** |
| 5% → 95% никто не проверяет | Крупный скачок ждёт проверки, в главную цифру не идёт | **ждёт Codex** (K15) | — |
| Заказчика в группу не добавишь | Ссылка заказчику с выбранными этапами | **ждёт Codex** | — |

Вывод: **сегодня отличие от WhatsApp слабое.** Без отчётов рабочих колонка «есть» — это журнал, который владелец ведёт сам. После этого PR рабочий может отчитаться по приглашению на почту, и отличие появляется для объекта и этапа. Сильное отличие (проверка скачков, ссылка заказчику) — только после Codex. До этого ни лендинг, ни приложение их не обещают.

WhatsApp не враг: это канал, где бригада уже общается. Цифры «экономит N часов» не используем — данных нет.

### 5.3. Что видит владелец в первый день (0 отчётов)

Принцип: нет данных ≠ нет проблем.

| Момент | Что видит | Главное действие |
|---|---|---|
| Сразу после регистрации | `create_company_and_profile` уже выполнен → пустой список: «Заведите первый объект» | «Создать первый объект» |
| Объект создан, никто не приглашён | этапы по 0%, серое кольцо «Никто не приглашён» | **«Пригласить рабочего»** (имя + почта); вторично «Пригласить бригадира» |
| Приглашение отправлено | «Приглашён {имя}, {дата}. Отчётов пока нет» | «Пригласить ещё раз» (вторично; главное остаётся за приглашением) |
| 3–6 дней от создания, отчётов нет | ▲ жёлтым «N дней без первого отчёта» | «Пригласить ещё раз» |
| 7+ дней | ■ красным «N дней без первого отчёта» | «Пригласить ещё раз» |
| Пришёл отчёт | лента: имя, этап, «было → стало», фото, время | открыть отчёт |

Пустые состояния называют следующий шаг и того, кто его делает:
- фото: «Фото появятся, когда рабочий отчитается» + «Пригласить рабочего»;
- проблемы: «Открытых проблем нет» — это нормальное состояние, а не «нет данных»;
- очередь проверки: «Нечего проверять».

Счётчик «N из 3 отчётов рабочих за 7 дней» на обзоре — **ждёт владельца**.

## 8. Решения для design-brief

1. **Блокер №1 закрывает этот PR:** экран отчёта вызывает `submit_stage_report` (фото + этап + % одним вызовом). `update_stage_progress` у рабочего не используется (K14).
2. **Сразу после `signUp` UI вызывает `create_company_and_profile`.** `ProfileNotConfigured` показывается только при ошибке, с «Проверить снова» и контактом.
3. **Главное действие дня 0 — «Пригласить рабочего»** (имя + почта → `api/invite.ts`, роль `worker`, этот объект). Тупиковых главных действий нет: WhatsApp-ссылку на `/login` убрать полностью. Личная ссылка без почты — после C3 [О2].
4. **Фирма без бригадира — основной случай.** Владелец приглашает и (после Codex) проверяет сам. Если бригадир есть, первое действие владельца — не проверка: проверка у владельца только для отчётов старше 48 ч [О3].
5. **Пакет «Подтвердить N мелких» никогда не включает скачки > 25.** Автор крупного скачка не может подтвердить его сам. Оба правила переданы Codex (K21, K22) [О4].
6. **«Не отправлено»** [О5]:
   - черновик в `localStorage` с ключом `bp:draft:{projectId}:{stageId}`, запись до первой попытки, в `try/catch`;
   - ввод не теряется при ошибке и переживает перерисовку;
   - «Отправить снова» повторяет с тем же путём фото;
   - при открытии страницы черновики показываются жёлтой плашкой и отправляются сами;
   - фоновую отправку из закрытой страницы не обещаем.
7. **Экран отчёта: ≤ 5 касаний (цель)** [О6]:
   - камера сразу (`capture="environment"`), галерея вторично;
   - этап выбран заранее (последний этап этого человека);
   - кнопки «−10 / +10 / +25 / 100%» ≥ 48 px;
   - ни ползунка, ни автосохранения; отправка только кнопкой «Отправить»;
   - лендинг показывает этот же экран.
8. **Одна шкала свежести: сегодня / 1–2 / 3–6 / 7+ дней** + «N дней без первого отчёта» от `projects.created_at` (3–6 жёлтое, 7+ красное). Серое только у объекта, где никто не приглашён. Шкала одна на список, обзор и лендинг (демо «5 дней» красным правит лендинг-PR) [О7].
9. **Активация** = ≥ 3 отчёта от людей с ролью `worker` за первые 7 суток от `projects.created_at`:
   - считаем отчёт `stage_reports` или фото рабочего (фото одного автора за 10 минут = один отчёт);
   - не считаем возвращённые, повторы, отчёты владельца и бригадира;
   - считается запросом §2.1, без аналитики в продукте [О8].
10. **Статусы.** Пока Codex не расширил `stage_reports` (K15), в продакшене все отчёты — «Принято». На ленте владельца стоит пометка «крупный скачок +N, не проверен». «Ждёт проверки ○» и «Проверено ✓» рисуем на заглушках `// TODO backend` и не показываем как работающие.
11. **Нет выдуманных чисел:** все пороги и бюджеты в документах помечены как «цель» или взяты из `decisions.md` / кода [О9].
12. **Обещания без продукта (§9) не повторяем в приложении.** Лендинг-PR убирает или смягчает каждое [О10].
13. **Оплату, пробный период, ссылку заказчика и телефоны не проектируем как работающие потоки** — только как пробелы (§10) [О11]. Пауза и завершение объекта, «Забыли пароль», «Задайте пароль» — в этом PR.
14. **Роли в тексте:** «Владелец», «Бригадир», «Рабочий», «Заказчик». Подпись кнопки отчёта везде одна — «Отчитаться». Сервер не отдаёт видимых строк (K24).
