## 1. Роли: продукт против кода

| Роль в продукте (`decisions.md`) | Роль в коде (`UserRole`, `db.ts`) | Подпись в `ru.json` | Как входит сейчас | Как должен входить |
|---|---|---|---|---|
| Владелец фирмы | `gc` | «Генподрядчик» | e-mail + пароль | e-mail + пароль, самостоятельная регистрация (`onboarding.md`) |
| Бригадир (manager) | `foreman` | «Прораб» | аккаунт, заведённый вручную | по приглашению (C3, `onboarding.md` правило 3) |
| Рабочий | `worker` | «Рабочий» | **аккаунт с паролем** | личная ссылка, без аккаунта и приложения (`worker_links`, `reports.md` §2) |
| Заказчик | `client` | «Заказчик» | аккаунт с доступом к объекту | ссылка только для чтения, со сроком и отзывом (`decisions.md` §2) |

Вывод: в интерфейсе называем роли «Владелец», «Бригадир», «Рабочий», «Заказчик». Подписи «Генподрядчик» и «Прораб» уходят из видимого текста (ключи в коде не трогаем до решения Codex). В контракте `reports.md` бригадир назван `manager`, в коде `foreman` — это одна роль, имя в БД решает Codex.

## 2. Метрики

Из `decisions.md` §4. Ничего не добавляем.

| Метрика | Определение | Что нужно, чтобы её посчитать | Можно посчитать сейчас? |
|---|---|---|---|
| **Активация** | объект с ≥ 3 отчётами рабочих за 7 дней | отчёт = строка `stage_reports` с `worker_link_id` (`reports.md` §1) | **Нет.** Сейчас «отчёт» = любая строка `stage_history` или `photos`, включая правки самого владельца. Отличить рабочего от владельца можно только по роли автора, и правка владельцем засчитается так же. |
| **Успех** | объект закрыт (`completed`) с открытой ссылкой заказчика | ссылка заказчика | Нет: ссылки заказчика нет. |
| **Удержание** | недельно активные объекты | отчёты рабочих по неделям | Нет, по той же причине, что активация. |

Следствие для дизайна: каждый экран владельца в первые 7 дней должен вести к **отчёту рабочего**, а не к тому, чтобы владелец сам двигал проценты. Отметка владельцем «первого этапа» не приближает активацию и прячет главный вопрос: начнёт ли бригада отчитываться.

Промежуточные шаги воронки (для чтения, а не для аналитики: аналитику не добавляем по `claude-code-app-redesign-team-prompt-v2.md`):
1. Аккаунт создан → 2. Компания настроена → 3. Первый объект создан → 4. Ссылка отправлена бригадиру/рабочему → 5. Первый отчёт рабочего → 6. 3 отчёта за 7 дней (активация) → 7. Первая проверка бригадиром → 8. Ссылка заказчику → 9. Объект закрыт со ссылкой заказчика (успех).

## 3. Пути по ролям

Формат: шаг → экран/маршрут → состояние в коде → главное действие экрана → цена ошибки (что теряется, если шаг сорвался).

### 3.1. Новый посетитель → регистрация

| # | Шаг | Экран / маршрут | В коде | Главное действие | Цена ошибки |
|---|---|---|---|---|---|
| 1 | Открывает сайт | `/` `LandingPage` | есть | «Начать — 30 дней бесплатно» | Уходит: потерян потенциальный клиент. Доверие режут плейсхолдеры имени/телефона/OÜ (`decisions.md` §7.1, критика §2) — **ждёт владельца** |
| 2 | Смотрит пример | `/` блок `DemoObjectSection` | есть (пример-схема, не кликабельное демо) | «Посмотреть пример» | Если пример расходится с экраном приложения, доверие падает после входа. Кликабельное демо — открытый вопрос `decisions.md` §7.3 |
| 3 | Регистрируется: e-mail + пароль | `/#start` `SignupSection` → `supabase.auth.signUp` | есть | «Создать аккаунт» | Ошибка формы = клиент ушёл. Если включено подтверждение e-mail, письмо приходит, а лендинг про него не говорит (`onboarding.md` вопрос 1) |
| 4 | Попадает в приложение | `/dashboard` → `ProfileNotConfigured` | **частично**: компания заводится вручную, текст «обычно в течение рабочего дня» | «Проверить снова» | **Самая дорогая точка воронки.** Человек пришёл с намерением сейчас, а получает ожидание до суток. Теряется весь импульс первого дня, а 30 дней пробного периода тикают. Закрывается RPC `create_company_and_profile` (`onboarding.md`) |
| 5 | Видит пустой список | `/dashboard`, пустое состояние `NextSteps` | есть | «Создать первый объект» | Если пустое состояние не говорит, что делать, владелец закрывает вкладку |

Метрика шага: пройти от 1 до 5 в одной сессии. Сейчас это невозможно без ручной настройки.

### 3.2. Владелец (`gc`)

| # | Шаг | Экран / маршрут | В коде | Главное действие | Цена ошибки |
|---|---|---|---|---|---|
| 1 | Входит | `/login` | есть | «Войти» | Забыл пароль: восстановления пароля в `Login.tsx` нет. Потерян вход, звонок владельцу продукта |
| 2 | Создаёт объект | `/dashboard` → `CreateProjectForm` (RPC `create_project_with_stages`) | есть; этапы из одного каталога `stage_templates` | «Создать объект» | Неверные этапы: шаблоны Новый дом / Ремонт квартиры / Ванная / Крыша / Пристройка и веса этапов (`decisions.md` §2) в коде **нет**. Ремонт ванной получит этапы дома, % будет врать |
| 3 | Отправляет ссылку бригадиру / рабочему | `/project/:id` → `InviteWorkerLink` (WhatsApp / копировать) | **частично**: ссылка ведёт на `/login`, не на личную ссылку | «Отправить ссылку в WhatsApp» | **Тупик.** Рабочий без аккаунта открывает `/login` и не может войти. Теряется первый отчёт и вера владельца, что «рабочие будут пользоваться». Закрывается `worker_links` (C3, `reports.md` §2) |
| 4 | Ждёт первый отчёт | `/dashboard`, `ReportStatusBadge` «Отчётов пока нет. Пригласите рабочего» / «ждём первый отчёт от {name}» | есть | «Отправить ссылку ещё раз» / «Скопировать ссылку» | Если «нет отчётов» выглядит как «всё в порядке», владелец не дожимает бригаду. Принцип «нет данных ≠ нет проблем» |
| 5 | Каждый день смотрит список объектов | `/dashboard` `ProjectListCard` | есть | открыть объект, у которого хуже всего свежесть | Объект «7+ дней без отчёта» не замечен = простой, который владелец оплачивает. Сортировка «худший сверху» в коде **нет** (порядок из запроса) |
| 6 | Открывает объект | `/project/:id` `ProjectDashboard` | **частично**: % = простое среднее этапов, без весов и без разделения принято/ждёт | зависит от состояния (см. §4) | Ложная готовность: 5 → 95 одним движением ползунка засчитывается сразу. Ошибочное решение об оплате бригаде — прямые деньги |
| 7 | Получает срочную проблему | `/project/:id/issues` | есть экран; уведомлений нет | «Назначить / закрыть» | Проблема без уведомления видна только когда владелец сам открыл приложение. Push + e-mail — v1 по `decisions.md`, бэкенда нет (`reports.md` вопрос 3) |
| 8 | Отвечает за просроченную проверку | очередь проверки | **нет** | «Проверить» | Через 48 ч без проверки отчёт эскалируется владельцу (`reports.md` §3). Без экрана эскалация некуда вести |
| 9 | Даёт ссылку заказчику | настройка видимости этапов + «предпросмотр как заказчик» | **нет** (есть только таблица видимости в контракте) | «Показать заказчику» | Ссылка с лишним (непроверенный % ) = спор о деньгах с заказчиком. По умолчанию всё скрыто (`decisions.md` §2) |
| 10 | Решает про тариф на 31-й день | `/tariff` | частично: только описание, «биллинга нет» | — (информационный экран) | Неясность «что будет на 31-й день» = страх заложника. Правило: без карты, ничего не списывается, объект «только чтение», напоминание за 5 дней (`decisions.md` §2, `pricing.ts`) |
| 11 | Закрывает объект | статус `completed` | частично: статус есть в `ProjectStatus`, сценария закрытия с ссылкой заказчика нет | «Завершить объект» | Закрытие ≠ отток (`decisions.md` §4). Без ссылки заказчика успех не засчитывается |

Главное действие владельца в продукте: **увидеть, где стоит работа, и толкнуть нужного человека.** Не «заполнить данные».

### 3.3. Бригадир (`foreman` в коде, `manager` в контракте)

| # | Шаг | Экран / маршрут | В коде | Главное действие | Цена ошибки |
|---|---|---|---|---|---|
| 1 | Получает приглашение от владельца | ссылка-приглашение | **нет** (C3; `onboarding.md` правило 3) | «Открыть объект» | Без приглашения бригадира нет, а он — тот, кто приводит рабочих. Сейчас его аккаунт заводят вручную |
| 2 | Раздаёт ссылки рабочим | экран «Люди объекта»: личная ссылка на каждого, отзыв, «открыта на другом телефоне» | **нет** (`worker_links`, `reports.md` §2). Есть общий `InviteWorkerLink` на `/login` | «Добавить рабочего и отправить ссылку» | Одна общая ссылка = нельзя понять, кто отчитался; личность рабочего не доказана (`decisions.md` §2) |
| 3 | Вешает лист «Как отчитаться» с QR | печатный лист | **нет** | «Распечатать лист» | Рабочий потерял сообщение в WhatsApp — нет второго пути к ссылке |
| 4 | Проверяет крупные скачки | очередь проверки: отчёты `pending` (скачок > 25) | **нет** (`review_stage_report`, `reports.md` §3) | «Подтвердить» (или «Вернуть» с причиной) | Не проверил 24 ч → напоминание; 48 ч → владельцу. Пока не проверено, главная цифра не растёт: владелец видит отставание, которого нет, или бригада ждёт оплату |
| 5 | Подтверждает день рабочего пакетом | там же, «Подтвердить всё за день» | **нет** (`review_worker_day`, `reports.md` §3) | «Подтвердить день» | Без пакетного подтверждения проверка превращается в 20 тапов, бригадир бросает её |
| 6 | Получает срочную проблему первым | `/project/:id/issues` | есть экран, уведомлений нет | «Взять в работу» | Проблема лежит без ответа |
| 7 | Отчитывается сам | `/project/:id/stages` | частично (ползунок без статусов) | «Отчитаться по этапу» | Отчёт бригадира без фото — то же, что слово в WhatsApp |

Главное действие бригадира: **подтвердить или вернуть крупный скачок с фото.** Это единственное место, где появляется «проверено ✓».

### 3.4. Рабочий

| # | Шаг | Экран / маршрут | В коде | Главное действие | Цена ошибки |
|---|---|---|---|---|---|
| 1 | Получает ссылку в WhatsApp или сканирует QR | личная ссылка | **нет**; сейчас ссылка на `/login` | — | Рабочий без пароля упирается в форму входа. **Отчёт потерян до того, как появился** |
| 2 | Открывает ссылку | экран рабочего (маршрут не определён; бэкенд — `worker_links.token`, `reports.md` §2) | **нет**. Ближайший аналог для аккаунта: `/project/:id/today` | «Отчитаться» (одна большая кнопка) | Если открылся не тот объект или не то имя — отчёт уйдёт не туда. Имя рабочего наверху экрана обязательно |
| 3 | Выбирает этап | список этапов объекта | частично: `Today` ведёт на `/stages` (`TODO(A2)` в `Today.tsx`) | выбрать этап | Ошибка этапа = % чужого этапа, ложная картина у владельца |
| 4 | Снимает фото | камера телефона | частично: фото и % — **разные действия** (`PhotoUploadForm` отдельно от `StageProgressControl`) | «Сфотографировать» | % без фото — непроверяемое слово. EXIF `taken_at` читается до сжатия (`reports.md` §1), иначе время съёмки неизвестно |
| 5 | Отмечает % | ползунок / кнопки | частично: ползунок с шагом 5 | выбрать % | Снижение % без причины. По контракту причина обязательна одним тапом: переделка / ошибка в учёте / снос (`decisions.md` §5.6) — в коде нет |
| 6 | Отправляет | три состояния: «Отправляется» / «Сохранено на телефоне, не отправлено» (жёлтая плашка) / «Отправлено ✓» | **нет** | «Отправить» | **Молчаливая потеря отчёта** — худшая ошибка продукта. Рабочий думает, что отправил, владелец думает, что рабочий не работал. Обещаем только: отправка идёт, пока страница открыта и есть сеть (`decisions.md` §2). Оффлайн-режим не обещаем |
| 7 | Видит результат | «Принято» или «Ждёт проверки ○» сразу после отправки | **нет** | «Ещё отчёт» | Рабочий не понимает, почему его 90% не видны: без статуса «ждёт проверки ○» это выглядит как ошибка или недоверие |

Главное действие рабочего: **отправить отчёт = фото + этап + %**. Один экран, одна кнопка.

### 3.5. Заказчик

| # | Шаг | Экран / маршрут | В коде | Главное действие | Цена ошибки |
|---|---|---|---|---|---|
| 1 | Получает ссылку от владельца | ссылка только для чтения, со сроком и отзывом | **нет**. Сейчас заказчик = аккаунт `client` с доступом к объекту и видит всё, что видит команда | — | Заказчик видит непроверенные % и внутренние проблемы → спор о деньгах, потеря доверия к подрядчику |
| 2 | Смотрит ход работ | страница заказчика: только `visible` этапы, только `accepted` и `confirmed`, для `pending` — последнее подтверждённое значение и тихое «обновляется» (`reports.md` §4) | **нет** | Посмотреть фото этапа (экран чтения; кнопки действия нет) | Без приписки «% — ход работ, не основание для оплаты» (`decisions.md` §2) заказчик требует вернуть деньги за «недоделанные 40%» |
| 3 | Ссылка истекла / отозвана | экран «Ссылка больше не действует» | **нет** | «Связаться с подрядчиком» (контакт подрядчика) | Тупик без контакта = звонок владельцу в раздражении |

Главное действие заказчика: **посмотреть, что сделано, с фото**. Писать он ничего не может.

Вопрос **ждёт владельца**: видит ли заказчик «принято» (со слов бригады) или только «проверено ✓». `decisions.md` §2 говорит «заказчик видит только проверенное», `reports.md` §4 — «только `confirmed` и `accepted`». Это противоречие, см. §6.

## 4. Один экран — одно главное действие

| Экран | Маршрут | Роль | Главное действие | Что меняется по состоянию |
|---|---|---|---|---|
| Лендинг | `/` | посетитель | «Начать — 30 дней бесплатно» | — |
| Вход | `/login` | все с аккаунтом | «Войти» | — |
| Компания настраивается | `/dashboard` (`ProfileNotConfigured`) | новый владелец | «Проверить снова» (до `create_company_and_profile`); после RPC экран показывается только при ошибке | — |
| Список объектов, пусто | `/dashboard` | владелец | «Создать первый объект» | — |
| Список объектов | `/dashboard` | владелец | открыть объект с худшей свежестью (он первым в списке) | «Создать объект» — вторичная кнопка, не жёлтая |

## 5. Ответы на вопросы критики

### 5.1. Чем это лучше WhatsApp-группы

Отвечаем только тем, что продукт делает. Разделяем «есть в коде сейчас» и «будет после контракта». На лендинге и в приложении можно говорить только о колонке «есть», остальное — после релиза соответствующего бэкенда.

| В WhatsApp-группе | В BuildProof | Статус |
|---|---|---|
| Фото тонут в ленте, через неделю их не найти | Фото привязаны к объекту и этапу, фильтр по этапу (`/project/:id/photos`) | есть |
| Процент — это слово в сообщении, никто его не считает | % по каждому этапу и общий % объекта | есть (общий % пока простое среднее, веса — после контракта) |
| Неизвестно, кто и когда последний раз отчитался | Свежесть отчёта на карточке объекта: формой и текстом | есть (пороги расходятся с `decisions.md`, см. §6) |
| Изменение % не оставляет следа | История изменений этапа (`stage_history`, `StageHistoryPanel`) | есть |
| Проблема теряется среди фото | Отдельный список проблем с приоритетом и ответственным | есть |
| «Было 5%, стало 95%» — никто не проверяет | Скачок > 25 пунктов ждёт проверки бригадира, в главную цифру не идёт до подтверждения | **после** `stage_reports` (`reports.md` §3) |
| Нельзя понять, кто прислал фото и когда его сняли | Личная ссылка на рабочего; «снято / отправлено», «время съёмки неизвестно», «был офлайн» | **после** `worker_links` и `stage_reports` |
| Заказчика в группу не добавишь: он увидит всё | Ссылка заказчику, по умолчанию всё скрыто, этапы включаются по одному | **после** страницы заказчика (контракт токена — ждёт Codex) |

Чего не говорим: «экономит N часов», «вместо 40 сообщений», любые цифры времени — их нет (правило «не выдумывать цифры»). Не говорим, что WhatsApp не нужен: **WhatsApp остаётся каналом доставки ссылки**. Мы не заменяем чат, мы забираем из него отчёты. Это снимает возражение «бригада уже сидит в WhatsApp».

### 5.2. Как снять страх «рабочие не будут пользоваться»

Только механика продукта, без обещаний.

1. **Нет аккаунта, пароля и приложения.** Личная ссылка открывается в браузере телефона. *Сейчас нарушено:* ссылка ведёт на `/login`. Пока C3 не готов, эту механику нельзя упоминать в приложении как существующую.
2. **Ссылка приходит туда, где рабочий уже есть** — в WhatsApp (кнопка `InviteWorkerLink` есть), и висит на стене листом с QR (нет).
3. **Один экран, одна кнопка «Отчитаться».** Фото + этап + % за один проход. *Сейчас:* фото и % — разные действия на разных экранах (`Today` → `/stages`; `TODO(A2)`).
4. **Рабочий видит, что отчёт дошёл:** «Отправлено ✓». Если не ушёл — жёлтая плашка «Сохранено на телефоне, не отправлено» и кнопка «Отправить снова». Повтор не создаёт дубль (`client_request_id`, `reports.md` §1).
5. **Мелкий отчёт не ждёт никого:** скачок ≤ 25 сразу «принято». Рабочего не наказывают ожиданием за ежедневный шаг.
6. **Пустота видна владельцу сразу:** «Отчётов пока нет, ждём первый отчёт от {имя}» (строка `reportStatus.noneWaiting` есть) и «N дней без отчёта» на карточке. Владелец не узнаёт через месяц, что никто не пользовался, — он видит это на второй день и звонит конкретному человеку.
7. **Бригадир — ответственный за внедрение, а не владелец.** Владелец отправляет одну ссылку бригадиру, бригадир раздаёт личные ссылки и проверяет скачки. Это переносит «заставить рабочих» на человека, который стоит рядом с ними.
8. **Рабочим бесплатно** (`pricing.ts`: «workers and clients are always free»). Владельцу не нужно считать места для рабочих.

Гарантия «если за 30 дней ни один рабочий не начнёт — деньги не спишем» из критики: **ждёт владельца** (по `claude-code-app-redesign-team-prompt-v2.md` гарантию решает владелец). Фактически денег за 30 дней и так не списывается (без карты), но формулировку как гарантию агенты не пишут.

### 5.3. Что видит владелец в первый день (день 0, ноль отчётов)

Принцип: **нет данных ≠ нет проблем.** Пустой экран не должен выглядеть как «всё хорошо» и не должен выглядеть как авария. Он должен показывать следующий шаг и того, кто его делает.

Сценарий дня 0 и что на экране:

| Момент | Что видит | Главное действие | Сейчас в коде |
|---|---|---|---|
| Сразу после регистрации | Пустой список: «Заведите первый объект» и 3 шага | «Создать первый объект» | есть, если компания настроена; иначе `ProfileNotConfigured` с ожиданием до рабочего дня |
| Объект создан, 0 отчётов | Обзор: этапы с 0%, серое кольцо «ещё не обновлялось» (не красное), блок «Что дальше» | **«Отправить ссылку бригадиру»** | главное действие сейчас «Отметить первый этап», ссылка рабочему — вторичная. **Меняем местами:** отметка владельцем не даёт активации |
| Ссылка отправлена, ответа нет | На карточке объекта: «Ждём первый отчёт от {имя}», время отправки ссылки | «Отправить ссылку ещё раз» | частично: строка есть, времени отправки ссылки нет (нужен `worker_links.created_at` / `last_seen_at`, `reports.md` §2) |
| Рабочий открыл ссылку, но не отчитался | «{имя} открыл ссылку, отчётов нет» | «Написать {имя} в WhatsApp» | нет (`last_seen_at`) |
| Первый отчёт пришёл | Фото, этап, %, статус «принято» или «ждёт проверки ○», счётчик «1 из 3 отчётов за 7 дней» | открыть отчёт | нет (`stage_reports`) |

Пустые состояния, которые обязаны толкать к действию (не «здесь пока пусто»):
- список объектов пуст → «Создать первый объект»;
- обзор, 0 отчётов → «Отправить ссылку бригадиру»;
- фото, 0 фото → «Фото появятся, когда бригада отчитается» + «Отправить ссылку бригадиру»;
- проблемы, 0 проблем → «Открытых проблем нет» (это нормальное состояние, кнопка «Сообщить о проблеме»); не путать с «нет данных»;
- очередь проверки пуста → «Нечего проверять» + сколько отчётов принято за сегодня;
- рабочий (аккаунт), нет задач → кнопка «Отчитаться» остаётся главной (сейчас так и есть).

Счётчик активации «N из 3 отчётов рабочих за 7 дней» на обзоре объекта в первые 7 дней — **ждёт владельца** (это видимая владельцу метрика, а не аналитика; решение о показе за владельцем).

| # | Где | Код | `decisions.md` / контракт | Влияние |
|---|---|---|---|---|
| K1 | Рабочий | роль `worker` с аккаунтом и паролем; `InviteWorkerLink` шлёт `/login` | личная ссылка без аккаунта (§2) | Тупик для рабочего, активация невозможна. Блокер C3 |

| K6 | Снижение % | без причины | причина одним тапом (§5.6) | История без объяснения откатов |
| K7 | Подписи ролей | «Генподрядчик», «Прораб» (`ru.json` `roles`) | владелец, бригадир (§2) | Владелец малой фирмы не называет себя генподрядчиком |
| K8 | Заказчик | аккаунт `client`, видит все этапы, фото, проблемы, только без правки | ссылка, всё скрыто по умолчанию, видны только выбранные этапы (§2) | Заказчик видит внутреннюю кухню и непроверенные % |
| K9 | Видимость для заказчика | — | `decisions.md` §2: «видит только проверенное»; `reports.md` §4: «только `confirmed` и `accepted`» | Противоречие внутри документов. **Ждёт владельца** |
| K10 | Шаблоны этапов | один каталог `stage_templates`, «7 типовых этапов» | 5 шаблонов, веса, правка за минуту (§2) | Неверные этапы для ремонтов |
| K11 | Регистрация | компания заводится вручную, «в течение рабочего дня» | регистрация → пустой список своей компании (`onboarding.md`) | Потеря импульса дня 0 |
| K12 | Отметка «последний отчёт» | `lastReportAt` = любая `stage_history` или фото, включая владельца | активация считает только отчёты рабочих (§4) | Владелец, двигающий ползунок сам, видит «отчёт сегодня» — ложная зелёная свежесть |
| K13 | Главное действие обзора дня 0 | «Отметить первый этап» (владелец сам) | активация = отчёты рабочих (§4) | Экран ведёт владельца не к активации |

## 8. Решения для design-brief

1. **Главное действие владельца на объекте с нулём отчётов — «Отправить ссылку бригадиру»** (до C3 — «Отправить ссылку рабочему»). «Отметить первый этап» становится вторичным. Цель экранов первых 7 дней — 3 отчёта рабочих, а не заполненные проценты.
2. **Одна жёлтая кнопка на экран.** Таблица §4 — обязательный список главных действий для UX и UI. На обзоре объекта главное действие выбирается по приоритету: проверить `pending` → напомнить при 3+ днях без отчёта → открыть последний отчёт.
3. **Роли в видимом тексте: «Владелец», «Бригадир», «Рабочий», «Заказчик».** Не «Генподрядчик», не «Прораб».
4. **Статусы только три и только так:** «Принято» / «Ждёт проверки ○» (скачок > 25) / «Проверено ✓». Знак ✓ — только для подтверждённого бригадиром. Главная цифра — по принятому и проверенному, рядом вторая «с учётом ждущих проверки».
5. **Свежесть — одна шкала на весь продукт:** сегодня / 1–2 дня / 3–6 дней / 7+ дней без отчёта; «нет отчётов» — серое кольцо и текст со следующим шагом, не красное и не зелёное. Плановая пауза выключает красное. Форма + текст всегда.
6. **Отчёт рабочего = фото + этап + % на одном экране, одна кнопка.** Три состояния отправки обязательны: «Отправляется» / «Сохранено на телефоне, не отправлено» (жёлтая плашка с «Отправить снова») / «Отправлено ✓». Оффлайн не обещаем.
7. **Каждое пустое состояние называет следующее действие и того, кто его делает** («ждём первый отчёт от {имя}»). «Нет данных» не рисуем как «всё хорошо».
8. **Экраны без бэкенда (экран рабочего по ссылке, очередь проверки, люди объекта, страница заказчика) проектируем по `reports.md` на заглушках с `// TODO backend`;** в видимом тексте не говорим о функциях, которых пользователь не может сделать сегодня.
9. **Против WhatsApp говорим только то, что есть** (§5.1, колонка «есть»): фото по этапам, % по этапам, свежесть, история, проблемы. Никаких цифр экономии времени. WhatsApp подаём как канал доставки ссылки, а не как врага.
10. **Каждый тупик имеет выход:** недействительная ссылка рабочего → «Написать бригадиру»; заказчика → «Связаться с подрядчиком»; «Компания настраивается» → «Проверить снова» и контакт.
