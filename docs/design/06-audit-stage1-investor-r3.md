### 1. HIGH — Экран `/tariff` в приложении продолжает обещать то, чего нет, хотя это зона этого PR
**Где:** `src/pages/Tariff.tsx` (выводит `tariff.lead`, `tariff.days`, `tariff.trial`, `tariff.included`, `tariff.invoice`);
`src/i18n/locales/ru.json:306–317`; 01 §3.2 шаг 12, §4 строка «Тариф», §8 п. 16 и п. 21, §9 п. 1–3, 14, 28.

§8 п. 21 говорит: «Обещания без продукта (§9) в приложении не повторяем». Но для приложения документ вычищает
только `tariff.trial` («только чтение», «напоминание»). Остальное остаётся на экране, где владелец решает, платить ли:
- `tariff.included`: «рабочие по личным ссылкам без лимита, страница для заказчика, выгрузка в PDF» — нет ни одного (C3, `client-links.md`, §9 п. 3);
- `tariff.lead`: «Рабочие и заказчики бесплатно» — у заказчика нет входа (§9 п. 28);
- `tariff.invoice`: «Счёт раз в месяц PDF-файлом… E-arve по запросу» — биллинга нет (K19);
- `tariff.days`: «Пауза не считается» — паузу этот PR как раз включает (§3.2 шаг 9), а считать нечем.

§9 п. 1–3 и 28 упоминают `tariff.*` в колонке «Где», но действие у них общее и помечено «рекомендация; окончательно —
владелец». Значит, исполнитель app-PR не обязан ничего менять, и BuildProof внутри продукта обещает то же, что §9
просит убрать с лендинга. Для скептика это хуже, чем на лендинге: обещание дано уже вошедшему клиенту, на экране оплаты.

**Исправление:**
- В §4 строку «Тариф» и §8 п. 16 дополнить: «этот PR в `ru.json` / `en.json` / `et.json`: `tariff.included` →
  "До {{managers}} владельцев и менеджеров, рабочие без лимита"; `tariff.lead` → без "и заказчики";
  `tariff.invoice` → убрать до K19 (или "Счёт — по договорённости, напишите нам" при заполненном `legal.ts`);
  `tariff.days` → без "Пауза не считается" до K19».

## MED

### 1. MED — Новое окно активации выпадает до создания объекта, если рабочий уже был в системе
**Где:** 01 §2.1, CTE `start`: `coalesce(min(u.created_at), p.created_at) as t0`; «Оговорки», п. 1.

`auth.users.created_at` — момент создания пользователя, а не выдачи доступа к **этому** объекту (`project_access`
без `created_at`, `000:34–37`). У фирмы с двумя объектами рабочий приглашён на первый в октябре. Владелец заводит
второй объект в ноябре и даёт тому же рабочему доступ переключателем. Для второго объекта `t0` = октябрь, окно
`[t0, t0 + 7 дней)` закрылось до рождения объекта. Отчётов в окне ноль, `activated = false` навсегда. Оговорка
«датирует первым приглашением» записана, но последствие — «каждый следующий объект фирмы не активируется никогда» —
не названо. Это ложный отрицательный результат по главной метрике для самого ценного клиента (2–5 объектов, §1).

**Исправление:** `greatest(coalesce(min(u.created_at), p.created_at), p.created_at) as t0`. В оговорках написать:
«для рабочего, уже бывшего в системе, окно начинается не раньше `projects.created_at`; точно — после K28».

### 5. MED — Лимит писем Supabase Auth не входит в шлюз, а «Отправить ссылку для входа» его не обрабатывает
**Где:** 01 §0.3 (шлюз, п. 1–3), §8 п. 1, §3.2 шаги 3, 3б, 3в, §4 «Ссылка отправлена».

Все письма — приглашения (`inviteUserByEmail`), вход (`signInWithOtp`), сброс пароля — идут через Auth и делят один
лимит отправки писем на проект. Он общий для всех компаний и по умолчанию низкий даже со своим SMTP; плюс пауза
между письмами на один адрес. Документ знает только лимит `invite_log` «20 в час» на компанию (§3.2 шаг 3).
Сценарий первых 5 фирм: несколько владельцев в один вечер приглашают бригады и жмут «Отправить ссылку для входа» —
Auth отвечает `429` / `over_email_send_rate_limit`. Для `signInWithOtp` в таблицах состояний такого кода нет.
Владелец видит «Письмо отправлено», а письма нет. Это тот же ложный статус, который r2 закрывал в MED 10.

**Исправление:**
- В шлюз §0.3 / §8 п. 1 добавить п. 4: «лимит писем Auth поднят под первые 5 фирм; значение записано в `test-log.md`».
- В §3.2 шаг 3б/3в и §4 «Ссылка отправлена»: ошибка `over_email_send_rate_limit` / `429` от Auth → «Слишком много
  писем за короткое время. Попробуйте через {N} минут», строка остаётся для повтора; «Письмо отправлено» — только по успешному ответу.
