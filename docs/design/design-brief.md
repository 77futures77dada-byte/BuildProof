## 0. Процесс (решения оркестратора, 2026-11-25)
- Ветка `claude/app-redesign` от `origin/main` 8f9d2e8, worktree `../Buildproof-claude-redesign`.
- `claude/fonts-cyrillic` пропущена по решению владельца: Plex убираем целиком.
- Скриншоты не делаем (решение владельца). Проверка вёрстки только по DOM через Playwright: `scripts/check-overflow.mjs`.
- Сборка: `ALLOW_PLACEHOLDERS=1 npm run build`, пока в `src/config/legal.ts` плейсхолдеры (данные владельца).
- Прогон после каждого шага: `node scripts/run-checks.mjs` (lint, build, test, check-tokens, check-ru-latin, check-overflow) → дописывает `docs/design/test-log.md`.
- `scripts/check-tokens.mjs`: до реализации работает в режиме отчёта (`--report`, считает нарушения, exit 0) — это baseline этапа 0. С первого коммита реализации включается строгий режим в `npm run lint`; с этого момента любое нарушение = красный шаг.
- Критики после каждого этапа: «Март» (владелец), «Бригадир на объекте», «Инвестор/скептик». Каждый — отдельный субагент без контекста процесса. Цикл до двух проходов подряд без HIGH и MED ≤ 3, максимум 4 цикла на этап.
- Не трогаем `supabase/`, `api/`, миграции. Не добавляем UI-библиотеки, аналитику, A/B.

## 1. Продуктовые принципы (из входных данных, не обсуждаются)
- «Нет данных ≠ нет проблем».
- Статусы отчёта: «Принято» / «Ждёт проверки» (скачок > 25 пунктов; значок — пустой круг, SVG) / «Проверено» (только то, что бригадир подтвердил; значок — галочка в круге, SVG). Состояния отправки — отдельный набор значков: «Отправляется» (стрелка-круг), «Не отправлено» (треугольник), «Отправлено» (одна галочка без круга). Символы ○ ✓ → ● ✗ в текстах интерфейса не пишем — только SVG.
- Оффлайн не обещаем; геолокацию, SMS, Telegram не обещаем.
- Касание ≥ 48 px; шрифт ≥ 17 px; статус всегда формой и текстом, не только цветом.
- Слово «реальное/реальный» запрещено → «фактический», «что отметила бригада».
- Никаких выдуманных клиентов, отзывов, цифр, фото; плейсхолдеры в видимом тексте не публикуем.

## 2. Решения ролей

### 2.0 Порядок (2026-11-25)
Этап 2 (исследование, шрифты) идёт параллельно с этапом 1: от бизнес-потока не зависит. Критики этапа 1 могут вернуть его.

### 2.1 Бизнес-поток (`01-business-flow.md`, 2026-11-25)
1. Объект с 0 отчётов → главное действие «Отправить ссылку бригадиру» (до C3 — «…рабочему»). «Отметить первый этап» — вторичное.
2. Одна жёлтая кнопка на экран (таблица §4 в 01). Обзор объекта: проверить pending → напомнить (3+ дня без отчёта) → открыть последний отчёт.
3. Роли в тексте: Владелец / Бригадир / Рабочий / Заказчик. Не «Генподрядчик», не «Прораб».
4. Статусы: «Принято» / «Ждёт проверки ○» (скачок > 25) / «Проверено ✓». Главная цифра — принятое+проверенное; рядом «с учётом ждущих проверки».
5. Свежесть одной шкалой: сегодня / 1–2 / 3–6 / 7+ дней. «Нет отчётов» — серое кольцо + следующий шаг. Пауза выключает красное.
6. Отчёт рабочего = фото + этап + % на одном экране; 3 состояния отправки, жёлтая плашка «не отправлено». Оффлайн не обещаем.
7. Каждое пустое состояние называет следующее действие и кто его делает. Тупиков нет.
8. Нет бэкенда → UI по `docs/contracts/reports.md` на заглушках `// TODO backend`; в тексте не обещаем то, что пользователь ещё не может сделать.

### 2.1б Бизнес-поток, редакция 3 (2026-11-26, после 2 кругов критики)
1. День 0: главное действие «Пригласить рабочего» (имя + почта, несколько строк за раз → `api/invite.ts` по разу на строку). Адрес текущего пользователя в строке не принимается.
2. **Почта — шлюз выпуска.** Пока свой SMTP и переменные Vercel не проверены на стенде, путь по почте нигде не называется готовым; кнопки приглашения и входа по почте за флагом сборки `VITE_EMAIL_GATE_OPEN` (пока выключен: день 0 = «Отметить первый этап» + «Приглашение рабочих включится после настройки почты»). Вход: 6-значный код из письма (`verifyOtp`) на той же странице, ссылка вторична (`pkce`). Для первых фирм — сопровождение основателем (ждёт владельца). Рабочий без почты: пути нет до C3 `worker_links`.
3. Вход и повторный вход: на `/login` «Войти по ссылке на почту» (`signInWithOtp`, `shouldCreateUser:false`), экран для `otp_expired`. Повторная ссылка от владельца — тот же `signInWithOtp`, не `api/invite.ts`.
4. Черновики отчёта: IndexedDB, запись на черновик, ≤ 10. Путь фото `{projectId}/{stageId}/{draftId}.jpg`, `upsert:false`, «уже существует» = успех. Перед повтором проверяем, нет ли отчёта с этим фото. Повтор сам: `online`, фокус, таймер — пока страница открыта. Устаревший черновик: «Не принято: этап уже N%» → «Отправить с новым %» / «Удалить». Для каждого кода ошибки RPC свой экран.
5. Плашка «не отправлено»: свой токен предупреждения (не цвет главной кнопки), SVG-значок, число черновиков, статус повтора.
6. Проверка скачка: одно касание, 5 с «Отменить» (запрос уходит после 5 с — RPC отмены нет), кнопка неактивна до загрузки превью. «Подтвердить все мелкие» никогда не берёт > 25.
7. Кнопки % одни для приложения и лендинга: «−10», «+10», «+25», «Готово 100%». Без автосохранения, явное «Отправить».
8. Фирма без бригадира — основной случай: проверяет владелец.
9. Пауза: без красного, ниже активных, чип «На паузе».
10. Контакты в тупиках и кнопка «Написать о продолжении» на тарифе — только если `legal.ts` заполнен; иначе блок скрыт. Даты конца пробного периода в UI нет (нечем считать).
11. Активация: отчёты рабочих (не владелец, не бригадир, без отклонённых и дублей), окно 7 суток от первого приглашения; пока считается SQL-запросом вручную.
12. Обещания без продукта (§9 в 01, 29 строк) убираются или смягчаются в PR лендинга. В hero остаются имя/телефон основателя (рендер только при данных), удаляется «Новый продукт, без громких обещаний».
13. Конфликты для Codex: K14–K32 в 01 §6 (`update_stage_progress` forbidden для рабочего, поля `stage_reports`, пакет включает > 25, самопроверка, `api/invite.ts` удаляет пользователя, нет «вошёл хоть раз», нет даты доступа, идемпотентность, нет RPC отмены проверки и др.).

### 2.2 Шрифт и исследование (`02-type.md`, `02-research.md`, 2026-11-25; до критики этапа 2)
- Фаворит: **Onest** variable (wght), @fontsource-variable/onest 5.3.1, OFL. Subsets latin + latin-ext + cyrillic = 76,2 КБ. Запасной: **Geologica** variable 5.3.0 (62,3 КБ).
- Отклонены по файлам: Inter (вес), Golos Text (tnum не выравнивает), Roboto Flex и PT Sans (нет tnum).
- Значки ○ ✓ → не входят в subset → статусные значки только inline SVG.
- Коды ссылок рабочих без I, l, 1, O, 0 (в шрифтах неразличимы).
- Ред. 2 (2026-11-26): Onest 39 / Geologica 38 из 50 — практически ничья; окончательный выбор после уличного теста на телефоне (протокол — в 02-type.md, ждёт владельца). Рабочий и бригадир: без начертания 400, цифры ≥ 600; `tnum` только в столбцах, датах, времени. Предзагрузка latin + cyrillic, fallback с метриками (Arial/Roboto).
- BuildProof — не официальный строительный дневник (ehituspäevik); выгрузку для него не обещаем.
- Довод о цене против Skywerk/Fieldwire держится не для всех размеров фирмы → цена и длина пробного периода решает владелец.
- Берём: «сделано» ≠ «проверено»; статус одинаков везде; рабочие бесплатно по ссылке; строитель решает, что видит заказчик; открытая цена и «без карты». Избегаем: демо за формой, доверие на цифрах масштаба, статус только цветом, обещания оффлайна, слабые реквизиты.

## 3. Ждёт владельца (собирается по ходу, итог — в PR)
- Реквизиты `src/config/legal.ts`: имя основателя, телефон, почта, OÜ, рег. код, KMKR, хостинг, почтовый провайдер, аналитика, срок DPA.
- Фото основателя и 3 предложения о себе.
- Свой SMTP + переменные Vercel для `api/invite.ts`, проверка на стенде (шлюз выпуска пути по почте); сопровождение первых фирм вручную.
- Цена (29 €/объект, потолок 99 €) против Skywerk/Fieldwire/Bauhub; длина пробного периода (30 дней против 2 месяцев у Bauhub); что происходит с данными после пробного периода; от чего считается пробный период (аккаунт или объект).
- Гарантия возврата / «деньги не спишем» — да или нет и формулировка.
- Реальные цифры («Уже N объектов») — только если правда.
- Скриншоты чатов WhatsApp «до» (с согласия людей).
- Тест черновиков и автоповтора на настоящем iPhone в режиме полёта.
- Уличный тест шрифта Onest vs Geologica на телефоне.
- Эстонские тексты — носитель языка.
- Что видит заказчик: только проверенное или принятое + проверенное (decisions vs `reports.md` §4).
