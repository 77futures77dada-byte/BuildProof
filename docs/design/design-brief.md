## 0. Процесс (решения оркестратора, 2026-11-25)
- Ветка `claude/app-redesign` от `origin/main` 8f9d2e8, worktree `../Buildproof-claude-redesign`.
- `claude/fonts-cyrillic` пропущена по решению владельца: Plex убираем целиком.
- Скриншоты не делаем (решение владельца). Проверка вёрстки только по DOM через Playwright: `scripts/check-overflow.mjs`.
- Сборка: `ALLOW_PLACEHOLDERS=1 npm run build`, пока в `src/config/legal.ts` плейсхолдеры (данные владельца).
- Прогон после каждого шага: `node scripts/run-checks.mjs` (lint, build, test, check-tokens, check-ru-latin, check-overflow) → дописывает `docs/design/test-log.md`.
- `scripts/check-tokens.mjs`: до реализации работает в режиме отчёта (`--report`, считает нарушения, exit 0) — это baseline этапа 0. С первого коммита реализации включается строгий режим в `npm run lint`; с этого момента любое нарушение = красный шаг.
- Критики после каждого этапа: «Март» (владелец), «Бригадир на объекте», «Инвестор/скептик». Каждый — отдельный субагент без контекста процесса. Цикл до двух проходов подряд без HIGH и MED ≤ 3, максимум 4 цикла на этап.
- Не трогаем `supabase/`, `api/`, миграции. Не добавляем UI-библиотеки, аналитику, A/B.

## 1. Продуктовые принципы (из входных данных, не обсуждаются)
- «Нет данных ≠ нет проблем».
- Статусы отчёта: принято / ждёт проверки ○ (скачок > 25 пунктов) / проверено ✓ (только то, что бригадир подтвердил).
- Оффлайн не обещаем; геолокацию, SMS, Telegram не обещаем.
- Касание ≥ 48 px; шрифт ≥ 17 px; статус всегда формой и текстом, не только цветом.
- Слово «реальное/реальный» запрещено → «фактический», «что отметила бригада».
- Никаких выдуманных клиентов, отзывов, цифр, фото; плейсхолдеры в видимом тексте не публикуем.

## 2. Решения ролей

### 2.0 Порядок (2026-11-25)
Этап 2 (исследование, шрифты) идёт параллельно с этапом 1: от бизнес-потока не зависит. Критики этапа 1 могут вернуть его.

### 2.1 Бизнес-поток (`01-business-flow.md`, 2026-11-25)
1. Объект с 0 отчётов → главное действие «Отправить ссылку бригадиру» (до C3 — «…рабочему»). «Отметить первый этап» — вторичное.
2. Одна жёлтая кнопка на экран (таблица §4 в 01). Обзор объекта: проверить pending → напомнить (3+ дня без отчёта) → открыть последний отчёт.
3. Роли в тексте: Владелец / Бригадир / Рабочий / Заказчик. Не «Генподрядчик», не «Прораб».
4. Статусы: «Принято» / «Ждёт проверки ○» (скачок > 25) / «Проверено ✓». Главная цифра — принятое+проверенное; рядом «с учётом ждущих проверки».
5. Свежесть одной шкалой: сегодня / 1–2 / 3–6 / 7+ дней. «Нет отчётов» — серое кольцо + следующий шаг. Пауза выключает красное.
6. Отчёт рабочего = фото + этап + % на одном экране; 3 состояния отправки, жёлтая плашка «не отправлено». Оффлайн не обещаем.
7. Каждое пустое состояние называет следующее действие и кто его делает. Тупиков нет.
8. Нет бэкенда → UI по `docs/contracts/reports.md` на заглушках `// TODO backend`; в тексте не обещаем то, что пользователь ещё не может сделать.
